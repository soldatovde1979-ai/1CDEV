# new-arch — Генератор архитектурного решения

Эта skill формализует ТЗ, бриф или устную постановку задачи в единый архитектурный документ уровня "готово к реализации ИИ-агентом или командой разработчиков без обратных вопросов". Применяется прежде всего к системам класса ETL / Pipeline / Batch-processing / интеграция систем с внешним обогащением (LLM, API), но структура достаточно универсальна для любой backend-системы с потоком данных источник → обработка → хранилище → выдача.

## Когда применять

- Пользователь прислал ТЗ / бриф / переписку с заказчиком и просит оформить это в архитектурный документ.
- Пользователь просит "сделать спеку как в приложенном примере" и приложил документ похожей структуры.
- Нужно зафиксировать архитектуру системы данных (источник → ETL → обогащение → отчётность) так, чтобы её можно было передать другому ИИ-агенту или команде разработки на реализацию без дополнительных согласований.
- НЕ применять для фронтенд-only задач, для чистых ML-исследований без потока данных, для документов, где нужен просто README или техническое задание в классическом смысле (без выделенной архитектуры/схемы БД/потоков) — в этих случаях просто пиши обычный документ, не насилуй пользователя 19 разделами.

## Как работать

### Шаг 0 — Аудит входных данных

Перед тем как писать документ, проверь присланное ТЗ по чек-листу ниже. Раздели найденные пробелы на **критичные** и **второстепенные**.

Чек-лист обязательной информации:

1. Источник данных — система, способ выгрузки (API/файл/БД/ручной ввод), формат обмена.
2. Транспорт между источником и обработчиком.
3. Объём и периодичность (записей/день, пики, частота выгрузки и обработки).
4. Механизм отслеживания изменений (watermark: по дате/ID/флагу, или полная перезагрузка).
5. Целевая схема данных — какие поля нужны на выходе, что из них чувствительное/персональное.
6. Внешнее обогащение — нужен ли LLM/API, модель, лимиты (RPS, батч), нужен ли fallback.
7. Требования к персональным данным — применимый закон (152-ФЗ, GDPR и т.п.), правила маскирования.
8. Хранилище — тип БД, ожидаемый объём, требования к производительности/индексам.
9. Отчётный/интерфейсный слой — кому и в каком виде отдаются результаты, частота обновления.
10. Инфраструктура — локально/сервер/облако, ОС, язык и стек, ограничения сети и безопасности.
11. Обработка ошибок — что критично, нужна ли DLQ, кол-во ретраев, куда девать битые данные.
12. Срок хранения / ретенция данных и файлов.
13. Критерии приёмки — если явно не сформулированы, вывести из функциональных требований.
14. Происхождение данных — откуда источник сам берёт актуальное состояние (рабочая база, копия, хранилище, эталон) и как синхронизируется с тем, где реально идут изменения.
15. Окружение исполнения — доступ к сети (есть ли интернет, как доставляются дистрибутивы), права (администратор или нет), установленные рантаймы и их версии.
16. Граница доверия — какие внешние сервисы (LLM, облачные API) получают данные или код и согласована ли такая передача.

**Если есть критичные пробелы** (обычно это пункты 1–8 и 14–16) — остановись и задай уточняющие вопросы одним компактным списком, не более 7 вопросов, каждый с однострочным обоснованием "почему это важно". Не генерируй документ, пока не получишь ответы, если пробел действительно блокирует однозначность архитектуры.

Формат вопросов:
```
Прежде чем сформировать спецификацию, нужно уточнить:
1. [вопрос] — почему важно: [1 строка]
2. [вопрос] — почему важно: [1 строка]
```

**Если пробелы второстепенные** (детали реализации, которые можно разумно предположить) — не блокируй генерацию, а фиксируй предположение прямо в документе под соответствующим разделом:
```
> ⚠️ Предположение: ...
```

### Шаг 1 — Структура документа

Генерируй документ строго по этой структуре (раздел можно сократить/пометить "Не применимо — обоснование", но не пропускать молча):

1. **Архитектурный манифест** — название, версия, однострочная цепочка компонентов.
2. **Назначение и охват документа** — цель, список охватываемых компонентов.
3. **Контекст и ограничения** — таблица: источник, транспорт, формат, объём, периодичность, внешние сервисы (приоритет/fallback), требования к ПД, интерфейс выдачи, безопасность, срок хранения.
4. **Подсистема выгрузки/приёма данных** — тип и режим запуска, механизм watermark (с алгоритмом/псевдокодом), точный запрос/алгоритм сбора (на синтаксисе платформы-источника, если известен), атомарная запись результата.
5. **Спецификация обмена данными** — структура каталогов/очередей, формат входящего сообщения (JSON-схема + пример), формат сообщения об ошибке.
6. **Схема хранилища** — DDL, индексы, обоснование выбора СУБД, служебные таблицы (аудит, идемпотентность).
7. **Архитектурные паттерны и стили** — базовый стиль + таблица «паттерн → где применяется → обоснование под эти конкретные объёмы/нагрузку».
8. **Структура проекта (Code Layout)** — дерево каталогов с комментарием к каждому модулю.
9. **Спецификация внешнего обогащения (LLM/API)** — системный и пользовательский промпт (если LLM) либо контракт API; параметры вызова; алгоритм батчевой обработки по шагам. Если потребитель выдачи системы — LLM или агент, обязателен **бюджет ответа**: лимит размера ответа, пагинация, выжимки вместо сырых данных, пометка обрезки.
10. **Обработка персональных/чувствительных данных** — норма закона, таблица маскирования, код-пример, явное указание про хранение исходников. Обязательна **таблица границы доверия** «что → уходит ли во внешний сервис → контроль», даже если ТЗ про ПД молчит: код, метаданные и коммерческая тайна — тоже чувствительные данные.
11. **Отчётный/интерфейсный слой** — для каждого артефакта: стек, частота обновления, содержание.
12. **Сценарии потоков (Sequence)** — минимум три: Happy Path, Error Path, Partial Failure/Timeout, пошагово.
13. **Контрольные точки (Checklist для приёмки)** — чекбоксы, выводимые из разделов 3–12.
14. **Развёртывание** — локальный запуск, автоматизация (cron/systemd/оркестратор — по контексту), запуск интерфейсного слоя.
15. **Требования к окружению и зависимостям** — таблица компонент/технология/версия. Для каждого рантайма — способ вызова (абсолютный путь, а не надежда на PATH), способ доставки (онлайн или офлайн-набор с контрольными суммами), нужны ли права администратора.
16. **Директивы для ИИ-исполнителя** — жёсткие неотменяемые правила реализации.
17. **Decision Log** — обоснование значимых выборов. Таблицы кандидатов недостаточно: из документа должно быть видно, почему выбран победитель. Структура раздела:
    - **17.0 Общие критерии** — 5–8 критериев с номерами (Кр-1…), выведенных из ограничений раздела 3, в порядке важности. Решения ссылаются на них по номеру.
    - **Сводная таблица** — «что выбираем → выбрано → ближайший соперник → решающий критерий».
    - **По каждому решению** отдельный подраздел:
      1. *Критерии* — какие из Кр-N решают именно здесь;
      2. *Кандидаты* — таблица «кандидат → вердикт» с пометкой источника у каждого;
      3. *Почему выбран X* — 3–5 предложений: как X закрывает критерии, со ссылками на Кр-N;
      4. *Почему не Y* — подробный разбор **ближайшего соперника**: его реальное преимущество и чем оно перевешено; остальные кандидаты — по одной строке с причиной отклонения;
      5. *Цена выбора* — что теряем, на что подписываемся;
      6. *Пересмотреть, если* — измеримое условие, при котором решение меняется, и на что.
    - Решение, которое пока нельзя принять, оформляется как «отложено»: критерии выбора и предварительная оценка фиксируются сейчас, срок решения — фаза или событие.
18. **Вопросы и ответы для разработчиков** — 5–8 вероятных вопросов с точными ответами.
19. **Заключительный контроль** — фраза о полноте, версия, дата, статус.

### Шаг 2 — Правила наполнения

- Конкретика везде: реальные имена полей, форматы дат, точные пороги (RPS, размер батча, ретраи, задержки) — никогда "настроить при необходимости".
- Если в ТЗ есть специфичная платформа-источник (1С, SAP, конкретная CRM и т.п.) — писать псевдокод/запрос на синтаксисе этой платформы, а не абстрактный SQL.
- Каждая таблица параметров самодостаточна — не заставлять читателя искать значение в другом разделе.
- Обоснование паттернов — конкретно под условия этого ТЗ (объём, нагрузка), а не общее определение паттерна из учебника.
- Раздел 16 формулировать императивами: "Обязательно", "Строго", "НЕ использовать".
- **Пометки достоверности.** Каждое утверждение о внешнем компоненте (возможности, версия, лицензия, зрелость, звёзды) — со ссылкой на источник или с пометкой «не проверено / по памяти». Утверждения без источника не могут быть единственным основанием выбора в разделе 17.
- **Go/No-Go.** Если требование держится на возможности стороннего компонента, которая не подтверждена первоисточником или помечена как экспериментальная, — в плане развёртывания обязательна проверка этой возможности до зависимых шагов и запасной вариант на случай провала.
- **Кто пишет куда.** Для каждого хранилища, каталога или ветки указать, кто в него пишет. Два независимых писателя в одно место (выгрузка и человек, сервис и агент) — обязательная развязка: разные каталоги или ветки, блокировка, механизм слияния. Молчаливая перезапись недопустима.
- **Происхождение данных.** Описать, откуда источник получает актуальное состояние и как синхронизируется (раздел 4). «Создать рабочую базу» без шага её наполнения — пробел.
- **Сверка с принципами.** Каждую фазу и каждый компонент сверить с принципами из раздела 1. Если компонент нарушает принцип (например, «не менять источник при чтении»), это явное исключение с ограничением области (только копия, только тест), а не молчаливое противоречие.
- Для ПД — назвать конкретную норму закона, если указана заказчиком; если не указана, но данные персональные — пометить как предположение и предложить наиболее вероятную норму по юрисдикции.
- Не добавлять технологии, не подразумеваемые ТЗ (не тащить Kafka под объём 100–500 записей/день).
- Писать на языке исходного ТЗ.

### Шаг 3 — Формат вывода

- Markdown, разделы `## N. НАЗВАНИЕ`.
- Таблицы — везде, где пары «ключ → значение» или «сущность → обоснование».
- Код/DDL/запросы — в блоках кода с указанием языка.
- Объём не сокращать искусственно: документ должен быть самодостаточным для реализации, за вычетом уточнений, заданных на Шаге 0.
- Если предполагается, что документ пойдёт как файл (а не просто в чат) — создать его как artifact/markdown-файл, а не просто вывести в текст ответа.

### Шаг 4 — Верификация покрытия (обязательна, выполняется после генерации документа)

Сразу после того как документ сгенерирован, не завершай ответ — выполни самопроверку и приложи её результат отдельным блоком после документа:

1. **Пройдись по исходному ТЗ построчно/по смысловым абзацам.** Для каждого требования, числа, названия поля, ограничения — найди, в каком разделе документа (1–19) оно отражено.
2. **Построй таблицу покрытия**:

   | Фрагмент ТЗ | Куда попало в спецификации | Статус |
   |---|---|---|
   | [краткая цитата или пересказ пункта ТЗ] | Раздел N — [что именно] | ✅ Учтено / ⚠️ Учтено частично / ❌ Не попало |

   В таблицу обязательно включать: все числовые значения (лимиты, сроки, объёмы, RPS, кол-во попыток), все названия полей/систем/сущностей, все требования безопасности и ПД, все явно упомянутые исключения и частные случаи.
3. **Отдельно выведи список "Не попало / попало частично"** — только те строки таблицы, где статус ⚠️ или ❌, с кратким объяснением причины (противоречит другому требованию / признано несущественным / не хватило контекста для однозначного решения — тогда это тоже повод для уточняющего вопроса, а не молчаливого пропуска).
4. **Если список "Не попало" пуст** — явно написать одну строку: "Все положения исходного ТЗ отражены в документе, пропусков не обнаружено."
5. **Проверка на противоречия.** Пройди документ и выпиши значения, которые встречаются больше чем в одном разделе: способ аутентификации, версии рантаймов, пути, выбранный компонент на каждую роль, имена файлов и переменных. Каждое значение должно совпадать везде. Расхождение — исправить до выдачи документа; если исправление требует решения пользователя — вопрос по формату Шага 0. Отдельно проверить, что на каждую роль выбран один компонент, а не «основной + для команды» с несовместимыми конфигурациями.
6. Если на Шаге 4 обнаруживается, что пропущенный фрагмент критичен для однозначности архитектуры — не молчать и не додумывать: вернуться к формату уточняющих вопросов из Шага 0, задать вопрос и дополнить документ после ответа, а не оставлять пробел с пометкой "не попало".

Эта проверка не заменяет предположения из Шага 0 (`⚠️ Предположение`) — предположения фиксируются по ходу написания документа, а таблица покрытия — это финальная сверка "вход vs выход" целиком, чтобы пользователь мог быстро увидеть, не потерялось ли что-то важное, не перечитывая оба документа вручную.

## Пример вызова

Пользователь: "Вот наше ТЗ на выгрузку заявок из Bitrix24, обработку через LLM и выдачу в Google Sheets. Сделай архитектурную спецификацию как для 1С Service Desk, которую я тебе давал раньше."

→ Применить Шаг 0 (проверить: платформа-источник Bitrix24 — ок; частота выгрузки указана? модель LLM указана? требования к ПД указаны? хранилище указано? отчётность = Google Sheets — но нужен ли ещё дашборд?) → при пробелах задать вопросы → сгенерировать документ по структуре из 19 разделов.

| Версия | Изменения |
|---|---|
| 1.1 | Раздел 17 переделан в Decision Log (критерии, ближайший соперник, цена, условие пересмотра). В Шаг 0 добавлены пункты 14–16 (происхождение данных, окружение исполнения, граница доверия). В разделы 9, 10, 15 — бюджет ответа для LLM-потребителя, таблица границы доверия, способ вызова и доставки рантаймов. В Шаг 2 — пометки достоверности, Go/No-Go, «кто пишет куда», происхождение данных, сверка с принципами. В Шаг 4 — проверка на противоречия. |
| 1.0 | Исходная версия. |
