# Research — исследование с управлением источниками

Консолидировано из двух проверенных скиллов:
- оркестрация параллельных агентов и протокол «поиск → запись» — altmbr/claude-research-skill;
- управление источниками, реестр цитирования, контр-рецензия — daymade/claude-code-skills (deep-research V6).

Адаптировано под Hermes: `web_search`, `web_extract`, `delegate_task`,
`write_file`/`read_file`. Без внешних скриптов и привязки к конкретному вендору.

## Активное исследование (текущий проект)

Тема: подключение MCP к 1С на рабочем месте «Windows + VS Code + агент в VS Code + 1С:Предприятие».

Цель — НЕ проектирование, а глубокая сборка базы знаний:
- собрать максимум источников (минимум 40) в единую базу знаний и проиндексировать;
- по каждому аспекту — сравнительные таблицы решений (особенно по правилам разработки 1С на GitHub — таблица для выбора).

Аспекты (ветки) и файлы результата:
1. Протокол MCP → `research/01-mcp-protocol.md`
2. MCP-клиенты/агенты в VS Code → `research/02-mcp-vscode.md`
3. Выгрузка/загрузка конфигурации 1С и автоматизация → `research/03-1c-config-export.md`
4. Существующие MCP-решения для 1С → `research/04-1c-mcp-solutions.md`
5. Правила/стандарты разработки 1С (GitHub) → `research/05-1c-dev-standards.md`
6. Язык 1С (BSL) и его инструменты → `research/06-1c-language-bsl.md`

Каждый файл: выводы по теме, сравнительная таблица (где применимо), раздел
«Источники» — нумерованный список «URL | название | тип | дата».

Сводка: `research/INDEX.md` — индекс + общий реестр всех источников.

Требования к источникам:
- каждый — с реальным рабочим URL из фактического поиска/извлечения (не выдумывать);
- тип: official / academic / secondary-industry / community / other;
- приоритет первоисточников: modelcontextprotocol.io и GitHub `modelcontextprotocol` (MCP); its.1c.ru, v8.1c.ru, dev.1c.ru, releases.1c.ru (1С); GitHub-репозитории (1c-syntax, silverbulleters, vanessa-automation и др.); статьи Infostart.

---

## Когда использовать

Запрос требует разобраться в теме по первоисточникам и свести в отчёт с
доказательствами. Не подходит для односложного вопроса «сколько сейчас время»
и для задач, где уже есть готовый ответ без проверки источников.

## Общий конвейер

```
P0  Уточнить вопрос + политика источников
P1  Декомпозиция на ветки + план → показать, ждать одобрения
P2  Скелеты файлов + параллельный запуск агентов
P3  Мониторинг, восстановление зависших
P4  Реестр цитирования + карта доказательств
P5  Синтез (черновик отчёта)
P6  Контр-рецензия (поиск слабых мест и противоречий)
P7  Проверка цитат и выдача
```

---

## P0. Уточнить вопрос и задать политику источников

1. Что именно надо выяснить? Для кого? Какое решение это должно поддержать?
   Если вопрос размыт — задай один уточняющий вопрос, не строй догадок.
2. Зафиксируй `AS_OF` — сегодняшнюю дату. Для всего, что зависит от времени,
   у каждой цитаты должна быть дата публикации.
3. Задай политику источников (см. P4) и определи глубину:
   - **Лёгкая** — один ограниченный вопрос, маленькая поверхность фактов;
   - **Стандартная** — несколько взаимосвязанных вопросов или спорные факты.
   Глубину выбирай по числу и последствиям неразрешённых вопросов, а не по
   желаемому объёму текста.

---

## P1. Декомпозиция на ветки + план

Разбей вопрос на 2–4 непересекающиеся ветки. Каждая ветка:
- одна связная подобласть, которой владел бы один специалист;
- 3–6 конкретных подразделов, которые надо написать;
- целевой объём ~200–500 строк markdown на ветку.

Пример для темы «MCP и 1С»:
- **Ветка 1 — Протокол MCP**: что это, архитектура (host/client/server),
  примитивы (tools/resources/prompts), транспорт (stdio/SSE/streamable HTTP),
  жизненный цикл.
- **Ветка 2 — Интеграция 1С**: как 1С может выступать сервером/клиентом MCP,
  существующие библиотеки и адаптеры, ограничения платформы.
- **Ветка 3 — Экосистема и практика**: готовые серверы, SDK, инструменты
  отладки, примеры внедрений, сравнение с альтернативами.

Покажи план пользователю и **жди явного одобрения**. Не запускай агентов до
подтверждения. Формат:

```
## План исследования: [тема]

### Ветка 1: [название]
Область: [1–2 предложения]
Разделы: 1. … 2. … 3. …
Файл: research/[тема]/agent-1.md

### Ветка 2: …
Файл: research/[тема]/agent-2.md

### Синтез (после всех веток)
Файл: research/[тема]/synthesis.md
```

---

## P2. Скелеты файлов

После одобрения создай каталог `research/[тема]/` и для каждой ветки —
скелетный файл с заголовками разделов и обязательной шапкой:

```markdown
# [Название ветки]

**Статус:** IN PROGRESS

## 1. [Первый раздел]

## 2. [Второй раздел]
```

Скелет даёт агенту структуру и делает прогресс измеримым (число строк /
заполненные разделы).

---

## P3. Запуск агентов и КРИТИЧЕСКИЙ протокол записи

Запускай ветки параллельно через `delegate_task` (одна задача на ветку). Каждая
задача получает: тему и границы ветки, абсолютный путь к своему файлу, список
разделов по порядку и протокол записи.

### Протокол «поиск → запись» (неотменяемый)

Главная причина зависших исследований — агент, который много ищет, но не пишет.
Правило одно и без исключений:

> После КАЖДОГО поиска или чтения страницы — немедленно записать результат в
> свой файл. Два поиска подряд без записи = нарушение протокола.

Для каждого раздела:
1. один поиск (`web_search`) или извлечение страницы (`web_extract`);
2. сразу дописать в файл, что узнал (в раздел этого шага);
3. при необходимости — следующий поиск;
4. снова сразу записать.

Если страница вернула ошибку (403/429/paywall) — сначала записать то, что уже
есть, и только потом пробовать другой URL. Каждое количественное утверждение и
каждый факт получают inline-ссылку на источник: `[Название](https://url)`.
Ссылки не собирают в конец — только рядом с фактом. По завершении всех разделов
агент меняет `Статус:` на `COMPLETE` и возвращает краткую сводку.

## P4. Мониторинг и восстановление зависших

Интервалы проверки по нарастающей (~30 с → 2 мин → 5 мин → далее каждые 5 мин).

Как проверять: читать файлы веток (число строк, какие разделы заполнены).
Проверка через `read_file`/`search_files`, не через длинный текст.

**Правило зависшего агента:** если между двумя проверками число строк в файле
не выросло — агент застрял. Не ждать, что он сам исправится (не исправится):
- `delegate_task action='steer'` — направить агента: «запиши уже найденное в
  файл, затем продолжай»;
- если не помогло — `delegate_task action='stop'` и перезапуск ветки с
  предзагруженными в prompt уже найденными данными и ещё более жёсткой
  формулировкой протокола.

Отчёт о проверке держи коротким: какие ветки пишут, какие разделы готовы, кто
завершён.

## P5. Реестр цитирования и карта доказательств

Когда все ветки завершены (или пользователь решил работать с тем, что есть):

1. Собери все источники из файлов веток, убери дубликаты по URL.
2. Присвой каждому порядковый номер `[n]` по первому появлению.
3. Пометь каждый источник типом и доступностью.

### Типы источников

`official` — первоисточник (официальная документация, спецификация, оф. блог);
`academic` — рецензируемое; `secondary-industry` — аналитика/обзоры;
`journalism` — новости; `community` — форумы/отзывы/Stack Overflow; `other`.

### Доступность

`public` — открыт всем; `semi-public` — нужна регистрация/лимиты (указывать в
отчёте); `exclusive` — платный/приватный доступ пользователя (использовать как
преимущество, но помечать).

### Правила

- Для «несущих» (load-bearing) утверждений — открыть первоисточник и
  убедиться, а не доверять пересказу из выдачи.
- Зависимые от времени факты — с датой публикации; свежесть против горизонта
  `AS_OF`.
- Источники ниже порога качества не «воскресают»: их либо явно исключают с
  причиной, либо не цитируют вовсе.
- Не выдумывать URL: каждая ссылка должна прийти из реального поиска/извлечения.

Затем карта доказательств: разложи выводы по разделам (по теме, а не по порядку
веток) и отметь для каждого: подтверждён / противоречив / неизвестен, какие
источники, какие контр-версии.

## P6. Синтез

Свести всё в один документ `research/[тема]/synthesis.md`:
- **Резюме** (3–5 тезисов);
- **Ключевые выводы по темам** (сквозные, не повторяющие ветки по очереди);
- **Противоречия и разногласия** между источниками;
- **Оценка уверенности** (что подтверждено хорошо, что требует проверки);
- **Пробелы** — что доказательства НЕ покрывают;
- **Рекомендуемые следующие шаги**.

Правила черновика: у каждого фактического утверждения — ссылка `[n]`; у чисел и
процентов — источник; у каждого раздела — маркер уверенности
(Высокая/Средняя/Низкая) с обоснованием; неподтверждённое помечать `[не
подтверждено]` или опустить.

---

## P7. Контр-рецензия и проверка

По каждому ключевому выводу проверь обратное:
1. Может ли вывод быть неверным?
2. Какие важные утверждения опираются на один источник/одно семейство источников
   (даже если доменов много)?
3. Какие утверждения не имеют источника, способного наблюдать этот факт напрямую?
4. Не используются ли устаревшие источники для срочных утверждений?
5. Выдавать только подтверждённые проблемы; ноль найденных проблем — допустимый
   результат, не выдумывать разногласия ради галочки.

Финальная проверка цитат: каждый `[n]` в отчёте есть в реестре; каждый
«несущий» вывод и каждая точная цифра/дата/цитата сходятся к первоисточнику.

---

## Анти-паттерны

- Считать первый черновик готовым без P7.
- Утверждение без ссылки или без карты доказательств.
- Доверять заметкам агентов как истине — их используют для навигации, а
  «несущие» выводы перепроверяют по первоисточнику.
- Выдумывать URL, данные или «воскрешать» исключённые источники.
- Смешивать противоречащие даты, не указывая расхождение.
- Пропускать `AS_OF` для зависящих от времени фактов.

## Доменные ориентиры: MCP и 1С

Первичные источники, которые стоит проверять первыми (и помечать как `official`):

- **MCP**: официальная спецификация — modelcontextprotocol.io; репозиторий
  `modelcontextprotocol` на GitHub (спека, SDK для TypeScript/Python/Java/Kotlin,
  примеры серверов). Транспорты: stdio, HTTP+SSE, Streamable HTTP. Версии спеки
  меняются — фиксировать дату/ревизию.
- **1С**: официальная документация ИТС (its.1c.ru), документация платформы
  «1С:Предприятие» (v8.1c.ru / releases.1c.ru), dev.1c.ru. Для интеграций —
  официальные репозитории 1С (github.com/1c-syntax и др.) и каталог внешних
  обработок/библиотек. Учитывать версию платформы (8.3.x) — поведение и
  доступные API зависят от неё.
- Отделять `community`-источники (форумы infostart.ru, Stack Overflow) от
  официальных: они полезны для практики, но не как первоисточник о поведении
  платформы.
