# Архитектурный Манифест v1.0

## Комплекс «MCP-интеграция 1С:Предприятие для AI-агента в VS Code»

**Дата:** 2026-10-14 | **Статус:** Проект (на согласование) | **Версия:** 1.0

---

## 1. Общие сведения и цели системы

### 1.1. Назначение

Система даёт AI-агенту внутри VS Code достоверный, структурированный доступ к трём
слоям знаний о проекте на платформе 1С:Предприятие:

1. **Конфигурация** — состав метаданных и тексты модулей (читается из автоматизированной
   выгрузки конфигурации, версионируется в git);
2. **Язык (BSL)** — синтаксис и семантика встроенного языка, разбор кода, сигнатуры;
3. **Правила разработки** — стандарты и диагностики (контроль качества кода).

Доступ реализуется через протокол **MCP (Model Context Protocol, ревизия спецификации
2026-07-28)**. Документ фиксирует выбор каждого компонента, обоснование выбора и план
развёртывания, достаточный для реализации другой ИИ-системой без участия автора.

### 1.2. Целевая среда

- ОС: Windows 10/11 (x64).
- Редактор: VS Code (1.99+).
- Агент: расширение-агент в VS Code (см. §3.1).
- Платформа: 1С:Предприятие 8.3.x (совместимость 8.3.16+; рекомендовано 8.3.24+).
- Хранилище кода: локальный git-репозиторий (возможен upstream на GitHub/GitLab).

### 1.3. Ключевые архитектурные принципы

- **Один источник истины — выгрузка конфигурации в git.** Всё, что агент «знает» о
  конфигурации, приходит из версионированной XML-выгрузки, а не из живой базы. Это
  даёт воспроизводимость, diff-историю и безопасность (чтение без касания рабочей базы).
- **Разделение на чтение и запись.** MCP-серверы по умолчанию read-only. Любая запись в
  базу (загрузка конфигурации, выполнение кода) — отдельный, явно авторизуемый контур.
- **Стандартные, зрелые компоненты.** Протокол — официальный MCP и его SDK; язык и
  правила — де-факто стандарт сообщества (BSL Language Server); выгрузка — штатный
  пакетный режим платформы. Минимум самописного.
- **Локальная изоляция по умолчанию (stdio).** Серверы запускаются как локальные
  процессы агента; сетевой HTTP-контур включается только при необходимости командного
  доступа.
- **Идемпотентность и свежесть.** Каждый ответ сервера помечен временем выгрузки; агент
  всегда знает, насколько актуальна картина конфигурации.

## 2. Архитектурная топология

```
┌─────────────────────────── VS Code ───────────────────────────┐
│  AI-агент (MCP-клиент: Cline / Roo Code)                      │
│    │ (stdio)                │ (stdio)                │ (stdio/HTTP)   │
│    ▼                        ▼                        ▼                ▼
│  MCP-сервер «1c-config»  MCP-сервер «BSL LS»     (опц) «1c-syntax»  (опц) live 1С
│  (Python, свой, read-only)(Java, --mcp)           синтакс-справка    1c_mcp/ROCTUP
│         │                        │                     │
│         ▼                        ▼                     ▼
│  XML-выгрузка конфигурации  BSL-парсер/диагностики   shcntx_ru.hbk
│  (git-репозиторий)                                   (справка по синтаксису)
└────────────────────────────────────────────────────────────────────┘
                  ▲
                  │ 1cv8 DESIGNER /DumpConfigToFiles (по расписанию + on-demand)
                  │
           1С:Предприятие (конфигуратор, пакетный режим)
```

### 2.1. Сущности

- **Конвейер выгрузки** — регламентный запуск `1cv8` в пакетном режиме конфигуратора,
  выгружающий конфигурацию в XML-иерархию (`/DumpConfigToFiles`) и коммитящий её в git.
- **MCP-сервер «1c-config»** — собственный лёгкий сервер (Python + официальный MCP SDK),
  который читает файлы выгрузки и публикует инструменты навигации по метаданным и коду.
- **MCP-сервер «BSL LS»** — BSL Language Server в MCP-режиме: разбор BSL, диагностики
  стандарта (правила разработки).
- **MCP-сервер «1c-syntax»** (опционально) — поиск по справке платформы (`shcntx_ru.hbk`):
  точные сигнатуры функций/методов/объектов языка.
- **MCP-клиент** — агент в VS Code, подключающий серверы как инструменты.

### 3.1. AI-агент (MCP-клиент) в VS Code

### 3.2. Источник истины: способ выгрузки конфигурации

| Кандидат | Автоматизация | Результат | Вердикт |
|---|---|---|---|
| **`1cv8 /DumpConfigToFiles` (пакетный режим)** | Высокая (CI/планировщик) | XML-иерархия (diff-совместима) | **Основной** — официальный, безлицензионный, скриптуемый, инкрементальный `-update` = 1–3 мин. |
| EDT (проект) + `1cedtcli`/`ring` | Высокая | проект EDT (текстовый) | Использовать, только если команда уже на EDT; тяжелее (Eclipse), сборка всё равно идёт через конфигуратор. |
| gitsync | Высокая | git-репозиторий из хранилища | Только при работе через **хранилище конфигурации**; иначе избыточен. |
| 1С:ГитКонвертер | Высокая | git (формат EDT) | Для разовой миграции истории хранилища >300 Мб/>1000 версий. |
| v8unpack (e8tools / saby) | Средняя | распаковка `.cf` | Нужен только для распаковки бинарных `.cf/.epf` без платформы; не штатный формат. |
| COM (V83.COMConnector) | Высокая | метаданные/данные, **не** полная выгрузка | Для live-доступа, не для выгрузки. |

**Решение:** конвейер выгрузки на `1cv8 DESIGNER /DumpConfigToFiles` (иерархический
формат) в git-репозиторий. Это и есть «автоматизированная выгрузка» из требования.
Загрузка обратно — штатный `/LoadConfigFromFiles` + `/UpdateDBCfg` — вынесена в
защищённый контур (см. §8).

### 3.3. MCP-сервер конфигурации (метаданные + код)

| Кандидат | Вердикт | Обоснование |
|---|---|---|
| **Свой read-only сервер поверх XML-выгрузки** | **Основной** | Детерминированный, не требует запущенной 1С, читает git-версию конфигурации, полный контроль инструментов. ~300 строк на официальном SDK. |
| VendaMax / MCP_1C_modules (Node.js по выгрузке) | Отклонён | Демо-реализация (статья написана с Grok), низкая зрелость. |
| smirnov0ser/mcp1c_metadata (Docker, JSON) | Отклонён | Один инструмент, узкий. |
| vladimir-kharin/1c_mcp (расширение+HTTP) | Фаза 2 (live) | Зрелый, но требует работающей базы + расширения + Python-прокси; для структурной информации избыточен и тяжелее. |
| ROCTUP/1c-mcp-toolkit | Фаза 2 (live) | Аналогично: для live-данных и `execute_query`, не для статической конфигурации. |

**Решение:** собственный MCP-сервер «1c-config» на официальном Python SDK (FastMCP),
транспорт `stdio`, read-only. Инструменты — §5.2.

### 3.4. MCP-сервер языка и правил (BSL)

| Кандидат | Вердикт | Обоснование |
|---|---|---|
| **BSL Language Server (`--mcp`)** | **Основной** | Де-факто стандарт сообщества 1c-syntax: 130+ диагностик (тег `STANDARD`), LGPL-3.0, нативный MCP-режим (stdio/SSE/streamable), тот же движок, что LSP. Закрывает и «язык» (парсинг), и «правила» (диагностики). |
| 1C-Company/v8-code-style | Дополнение (EDT) | Официальный норматив, но только как плагин 1C:EDT — не MCP. Использовать, если команда на EDT. |
| its.1c.ru/db/v8std | Дополнение | Официальная методичка (текст), не исполняемый компонент. |
| silverbulleters/standards | Не существует | Репозиторий удалён (404), содержимое влилось в 1c-syntax. |

**Решение:** основной — **BSL Language Server в MCP-режиме**; он даёт агенту и разбор
языка, и контроль правил. Официальный v8-code-style — дополнение для команд на EDT.

Подтверждено по первоисточнику: нативный MCP-режим
(`java -jar bsl-language-server.jar mcp`, транспорты stdio/sse/streamable) —
экспериментальная фича на Spring AI 2.0; инструменты `list/register_workspace_folder`,
`type_info`, `global_member_info` и др. Требование Java — **17+** (поддерживаются
17/21/23), рекомендуется Temurin/AdoptOpenJDK. Отдельный мост `mcp-bsl-lsp-bridge`
**не нужен** — он дублирует нативный MCP-режим BSL LS.

Для чтения живой базы (метаданные, формы, SELECT-запросы, код по имени объекта)
выбираем лёгкий сервер, а не связку «расширение + прокси»:

| Кандидат | Вердикт | Обоснование |
|---|---|---|
| **feenlace/mcp-1c** | **Основной (Phase 2)** | Один статический Go-бинарник (без Python/Node/Docker), 11 инструментов, MIT, 243★, активен (2026-10). Автоустанавливает служебное расширение в базу и публикует HTTP-сервис. Read-only. |
| vladimir-kharin/1c_mcp | Альтернатива | Богаче (кастомные tools/resources/prompts), но тяжелее: расширение + Python-прокси + OAuth2-обвязка. |
| ROCTUP/1c-mcp-toolkit | Альтернатива | Метаданные + данные + execute_query, но через `.epf` или Docker-прокси. |
| INFATON (51 инструмент) | Альтернатива | Самый функциональный, но привязка к типовым конфигурациям (ERP/БП/УТ/КА). |

**Обязательно при публикации:** HTTP-сервис `mcp-1c` публикуется на Apache/IIS —
закрыть его аутентификацией (Basic + TLS) и ограничить `localhost`/внутренним
сегментом; учётные данные в конфиг агента передавать через переменные окружения.
Без этого публикация отдаёт структуру базы любому, кто достучится до порта.

## 5. Спецификация компонентов

### 5.1. Конвейер выгрузки (автоматизация)

Пакетный сценарий выгрузки конфигурации в XML и фиксации в git (файл
`tools/export-config.cmd`):

```bat
@echo off
set BIN=C:\Program Files\1cv8\8.3.24.xxxx\bin\1cv8.exe
set REPO=D:\projects\1c\src
set BASE=File=D:\projects\1c\work-ib
set LOG=D:\projects\1c\logs

"%BIN%" DESIGNER /IBConnectionString "%BASE%" /DisableStartupDialogs ^
  /DumpConfigToFiles "%REPO%\cf" -Format иерархический -update ^
  /Out "%LOG%\dump.log"
if %errorlevel% neq 0 exit /b %errorlevel%

cd /d "%REPO%"
git add -A && git commit -m "config: automated export %date% %time%" || exit /b 0
```

- `-update` — инкрементальная выгрузка (1–3 мин вместо 25–45 мин полной).
- Расписание: **Windows Task Scheduler** (ежедневно ночью) + возможность ручного запуска.
- Полная выгрузка (без `-update`) — при первичном развёртывании.
- Загрузка обратно (только по явному запросу, в защищённом контуре):

```bat
"%BIN%" DESIGNER /IBConnectionString "%BASE%" /DisableStartupDialogs ^
  /LoadConfigFromFiles "%REPO%\cf" /UpdateDBCfg -Dynamic- /Out "%LOG%\load.log"
```

### 5.2. MCP-сервер «1c-config» (Python, FastMCP)

Инструменты (tools):

| Инструмент | Аргументы | Назначение |
|---|---|---|
| `list_metadata_objects` | `type?`, `subsystem?` | Список объектов метаданных (по типу/подсистеме). |
| `get_object_metadata` | `full_name` | XML-описание объекта (реквизиты, измерения, формы…). |
| `get_module_text` | `full_name`, `module` | Текст модуля (объекта/менеджера/формы/команды). |
| `search_objects` | `query` | Поиск объектов по имени/синониму/комментарию. |
| `search_in_modules` | `pattern`, `max_hits?` | Поиск вхождения по текстам модулей. |
| `list_subsystems` | — | Дерево подсистем. |
| `export_status` | — | Время последней выгрузки и git-коммит (свежесть). |

Скелет (FastMCP):

```python
from mcp.server.fastmcp import FastMCP
import xml.etree.ElementTree as ET, os, subprocess

CF_DIR = os.environ.get("ONEC_CF_DIR", r"D:\projects\1c\src\cf")

mcp = FastMCP("1c-config")

@mcp.tool()
def export_status() -> str:
    out = subprocess.run(["git", "-C", os.path.dirname(CF_DIR), "log", "-1",
                          "--format=%h %ci %s"],
                         capture_output=True, text=True).stdout.strip()
    return f"export dir={CF_DIR}; last commit={out}"

@mcp.tool()
def list_metadata_objects(type: str | None = None) -> list[str]:
    ...  # обход каталога CF_DIR/Configuration, чтение *.xml

if __name__ == "__main__":
    mcp.run()  # stdio по умолчанию
```

Правила: read-only, пути только внутри `CF_DIR` (защита от path traversal), ответы
кэшируются по mtime файлов выгрузки.

### 5.3. MCP-сервер «BSL LS» (язык + правила)

Запуск (Java 17+, поддерживаются 17/21/23; рекомендуется Temurin):

```bash
java -jar bsl-language-server.jar mcp --protocol stdio
# или streamable:  java -jar bsl-language-server.jar mcp --protocol streamable --server.port=8080
```

- Даёт парсинг BSL и диагностики стандарта (тег `STANDARD`) — тот же движок, что LSP.
- Workspace регистрируется инструментом `register_workspace_folder` (MCP `roots`
  deprecated в ревизии 2026-07-28), затем `type_info` / `global_member_info` /
  `global_member_search` и др.
- Режим экспериментальный (Spring AI 2.0) — API может меняться.

### 5.4. Конфигурация агента

**Roo Code** — проектный `.roo/mcp.json` (коммитится в git, подхватывается командой):

```json
{
  "mcpServers": {
    "1c-config": {
      "command": "python",
      "args": ["C:/tools/1c-config/server.py"],
      "env": { "ONEC_CF_DIR": "D:/projects/1c/src/cf" }
    },
    "bsl-language-server": {
      "command": "java",
      "args": ["-jar", "C:/tools/bslls/bsl-language-server.jar", "mcp", "--protocol", "stdio"]
    }
  }
}
```

**Cline** — тот же объект `mcpServers` в `cline_mcp_settings.json` (или UI → Configure
MCP Servers).

**VS Code Copilot/Cody** — ключ верхнего уровня `servers` в `.vscode/mcp.json`.

> Ловушка переносимости: Cline/Roo/Cursor/Copilot-CLI используют ключ `mcpServers`;
> VS Code/Cody — `servers`; тип транспорта Cline пишет `streamableHttp` (camelCase),
> Roo/GitHub — `streamable-http`. Для наших локальных stdio-серверов транспорт не
> указывается, конфликт не возникает.

### 5.5. MCP-сервер «mcp-1c» (live-доступ, Phase 2)

Установка (авто): `mcp-1c.exe --install "путь\к\базе" [--platform-version 8.3.XX]` —
ставит служебное расширение и обновляет конфигурацию БД (нужен эксклюзивный доступ:
база закрыта в Конфигураторе/клиенте). Затем публикация HTTP-сервиса в Конфигураторе:
`Администрирование → Публикация на веб-сервере` (Apache/IIS), имя публикации `mcp1c`.

Подключение в `.roo/mcp.json` (учётные данные — через env, не в открытом виде):

```json
{
  "mcpServers": {
    "1c": {
      "command": "C:\\Tools\\mcp-1c\\mcp-1c.exe",
      "args": ["--base", "http://localhost/mcp1c/hs/mcp-1c"],
      "env": { "MCP1C_USER": "...", "MCP1C_PASSWORD": "..." }
    }
  }
}
```

Проверка: `curl http://localhost/mcp1c/hs/mcp-1c/version`.

### 5.6. Правила разработки (статические) и токен-экономия (Phase 2)

- **Правила:** файлы `ai_rules_1c` (comol) кладутся в `.roo/rules-code/*.md` — Roo Code
  подхватывает их в системный промпт автоматически. Внимание: (1) у репозитория **нет
  лицензии** — для дирекции уточнить право использования; (2) часть файлов — только
  заголовки (полный текст раздаётся их Docker MCP-сервером), брать лишь полнотекстовые.
- **Токен-экономия:** `rlm-tools-bsl` (Dach-Coin, MIT, 208★) — 6 MCP-инструментов,
  SQLite-индекс методов и графа вызовов, `git_search` через `git grep`, без Docker/RAG.
  Полезен на крупных конфигурациях (ERP/УХ); на пилоте — опционально, Python 3.10+.

## 6. Алгоритм работы (типовой цикл)

1. **Планировщик** (ночью) выгружает конфигурацию → git-коммит (свежая «картина»).
2. Разработчик открывает проект в VS Code; агент (Cline/Roo) стартует MCP-серверы
   `1c-config` и `bsl-language-server` (stdio, локально).
3. Запрос вида «как устроен документ РеализацияТоваровУслуг» →
   `list_metadata_objects`/`get_object_metadata`/`get_module_text` (из выгрузки).
4. Запрос «найди, где вызывается процедура X» → `search_in_modules`.
5. Запрос «проверь код на стандарт» / «исправь ошибку» → BSL LS (диагностики).
6. Свежесть гарантируется `export_status`: агент сообщает дату последней выгрузки.
7. При необходимости точной справки по функции платформы → (Phase 2) `1c-syntax`.
8. Загрузка изменений в базу — НЕ через MCP по умолчанию, а защищённым контуром §8.

## 7. План развёртывания (пошагово)

1. **Подготовка.** Установить Python 3.11+, Java 17+, git. Получить дистрибутив
   платформы 1С (releases.1c.ru) и права на запуск `1cv8 DESIGNER`.
2. **Выгрузка.** Создать рабочую файловую ИБ, выполнить первичную
   `/DumpConfigToFiles` в git-репозиторий, закоммитить.
3. **Сервер конфигурации.** `pip install mcp`, развернуть `server.py` (§5.2), проверить
   `export_status` вручную.
4. **BSL LS.** Скачать `bsl-language-server.jar` (релизы 1c-syntax), проверить
   `java -jar ... mcp --protocol stdio` (должен ответить на `initialize`).
5. **Агент.** Установить Cline (или Roo Code), добавить MCP-серверы (§5.4), проверить,
   что инструменты появились в списке tools агента.
6. **Автоматизация.** Создать задачу в Task Scheduler на `export-config.cmd`.
7. **Контроль качества.** Прогнать сценарии §6; сверить `export_status` с реальной датой
   последней выгрузки.
8. **Команда.** Для развёртывания на дирекцию — Roo Code с коммитом `.roo/mcp.json`,
   пути вынести в переменные окружения (не хардкодить).

## 8. Безопасность и лучшие практики

- **Read-only по умолчанию.** Все MCP-серверы читают выгрузку; запись в базу
  (`/LoadConfigFromFiles`, выполнение кода) — отдельный контур с явным подтверждением
  и журналированием (ЖурналРегистрации 1С).
- **Секреты.** Учётные данные 1С (`/N` `/P`) не хардкодить: использовать переменные
  окружения или Secret Store; в CI — защищённые переменные.
- **Path traversal.** Сервер `1c-config` принимает только пути внутри `CF_DIR`, без
  `..`; полные имена объектов валидируются по списку из выгрузки.
- **Изоляция.** stdio-транспорт держит серверы в границе машины; HTTP/Streamable —
  только при осознанной публикации, с TLS и OAuth2 (не Basic).
- **Свежесть.** Всегда показывать дату выгрузки; при устаревшей картине — предложить
  перевыгрузку, а не отвечать по старым данным.
- **Git как источник истины.** Изменения конфигурации идут через git (code review),
  а не через прямое редактирование базы агентом.

## 9. Реестр рисков и trade-offs

| Решение | Плюсы | Минусы / Риски | Компенсация |
|---|---|---|---|
| Свой MCP-сервер вместо готового | Полный контроль, нет зависимостей от живых проектов | Сопровождение своими силами | ~300 строк, официальный SDK, покрытие тестами инструментов |
| Выгрузка по расписанию (не realtime) | Безопасно, воспроизводимо, git-история | Лаг между базой и «картиной» | `export_status` + on-demand перевыгрузка; инкрементальный `-update` (1–3 мин) |
| stdio-транспорт | Просто, локально, без сети | Серверы на каждой машине разработчика | Конфиг в git (`.roo/mcp.json`) + скрипт установки |
| BSL LS (сообщество) вместо официального | Зрелость, MCP-режим, де-факто стандарт | Не от фирмы 1С | Дополнять v8-code-style (EDT) при необходимости |
| Отказ от live-сервера на старте | Меньше поверхность атаки, проще | Нет live-данных/execute | Phase 2: vladimir-kharin/1c_mcp или ROCTUP под отдельный контур |

## 10. Дорожная карта

- **Phase 1 (ядро, пилот):** автоматическая выгрузка `1cv8 /DumpConfigToFiles` → git +
  сервер `1c-config` + BSL LS (нативный MCP) + агент Cline/Roo. Всё бесплатное/open-source.
- **Phase 2 (расширение):** live-сервер `mcp-1c` (feenlace) с аутентификацией,
  статические правила `ai_rules_1c` в `.roo/rules-code/`, опционально синтаксис-справка
  `1c-syntax` и `rlm-tools-bsl` (токен-экономия).
- **Phase 3 (команда):** централизованный HTTP-контур с OAuth2, CI-сборка из git
  (`/LoadConfigFromFiles` + `/CheckModules`).
