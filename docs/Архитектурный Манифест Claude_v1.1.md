## 1. АРХИТЕКТУРНЫЙ МАНИФЕСТ

**Цепочка компонентов:**

```
ИБ разработки ──1cv8 DESIGNER /DumpConfigToFiles──► git: ветка base (worktree erp-base)
   ▲                                                      │ git merge base
   │ (ручной, -Apply) load-changes.ps1                    ▼
   └──────────────────────────────────────────── git: ветка main (worktree erp) ◄── правки агента (*.bsl)
                                                          │ читают
                    ┌─────────────────────────────────────┼──────────────────────────┐
                    ▼                                     ▼                          ▼
          MCP «1c-config» (Python, stdio)      MCP «bsl-ls» (Java, stdio)   VS Code + Language 1C (BSL)
          метаданные, код, поиск,              type_info, global_member_*   подсветка, Problems
          check_module (BSL LS analyze)        (экспериментальный)
                    └──────────────┬──────────────────────┘
                                   ▼
                     Zoo Code / Roo Code (MCP-клиент) ──► DeepSeek API
```

**Ключевая идея редакции:** три слоя знаний (конфигурация, язык, правила) гарантированно
закрываются **одним своим read-only сервером** `1c-config`. Он не зависит от того, что умеет
экспериментальный MCP-режим BSL LS. Нативный MCP BSL LS подключается как дополнение для
справки по глобальному контексту платформы и отключается без потерь, если не прошёл Go/No-Go.

## 2. НАЗНАЧЕНИЕ И ОХВАТ ДОКУМЕНТА

**Цель:** дать AI-агенту в VS Code достоверный структурированный доступ к конфигурации 1С
(метаданные и код), к языку BSL и к правилам разработки. Чтение — из версионированной
XML-выгрузки; база при чтении не нужна. Документ достаточен, чтобы другая ИИ-система
реализовала решение без обратных вопросов, за вычетом открытых вопросов §18.2.

**Охват:**

| Компонент | Фаза | Статус |
|---|---|---|
| Конвейер выгрузки `export-config.ps1` + расписание | Ф1 | ядро |
| Модель веток `base`/`main` | Ф1 | ядро |
| MCP-сервер `1c-config` (свой, Python) | Ф1 | ядро |
| BSL LS: `analyze` (через `1c-config`) + нативный MCP | Ф1 | ядро / дополнение [GO] |
| Правила агента `.roo/rules/` (свои тексты) | Ф1 | ядро |
| Обратный контур `load-changes.ps1` (частичная загрузка в ИБ разработки) | Ф1.5 | опция |
| Live-доступ к копии ИБ (выбор сервера — §17.11) | Ф2 | расширение |
| `rlm-tools-bsl`, `ai_rules_1c` | Ф2 | расширение |
| Команда: CI-анализ, общий конфиг, OAuth2 | Ф3 | развитие |

**Вне охвата:** запись в рабочую ИБ; автоматическая загрузка без человека; локальная LLM
(упомянута как альтернатива в §17); EDT-контур.

## 4. ПОДСИСТЕМА ВЫГРУЗКИ

### 4.1. Тип и режим запуска

Скрипт `scripts/export-config.ps1` (PowerShell 5.1, файл в UTF-8 **с BOM**), версия 1.0.
Запускается тремя способами, все идемпотентны:

| Триггер | Команда | Назначение |
|---|---|---|
| Планировщик Windows, 02:30, `StartWhenAvailable`, `IgnoreNew` | `export-config.ps1` | Ночная картина |
| Задача VS Code `runOn: folderOpen` | `export-config.ps1 -IfOlderThanHours 12` | Свежесть, если ПК ночью выключен или Планировщик запрещён политикой |
| Задача VS Code вручную | `export-config.ps1` / `-Full` | По требованию |

### 4.2. Механизм отслеживания изменений (watermark)

- Платформенный: `ConfigDumpInfo.xml` в каталоге выгрузки. При наличии — `-update` (выгружаются только
  изменённые объекты); при отсутствии — полная выгрузка. Файл в `.gitignore`, он живёт только в worktree `base`.
- Логический: `last-dump.json` в `C:\1C\logs` — пишется **при каждом запуске**, в том числе при ошибке;
  поле `last_ok` переносится из прошлого статуса, если текущий запуск упал.
- git: коммит в `base` создаётся, только если есть изменения; автор `1C export <export@localhost>` —
  отличается от человека и агента.

### 4.3. Алгоритм

```text
1. Если задан -IfOlderThanHours N и last_ok моложе N часов → выход 0 («свежая»).
2. Захватить lock-файл logs\export.lock (эксклюзивное открытие). Занят → выход 0 («уже идёт»).
3. Проверить переменные: ONEC_BIN, ONEC_IB_PATH | ONEC_IB_SERVER; опц. ONEC_USER/ONEC_PASSWORD.
4. Если в erp-base есть незакоммиченные изменения в src/cf (след прерванного запуска):
      git reset --hard; git clean -fdx src/cf; режим := full.
   (worktree base принадлежит только скрипту — откат безопасен.)
5. Режим := full, если -Full или нет ConfigDumpInfo.xml; иначе update.
6. full: очистить src/cf через git rm + git clean (корректно с длинными путями, удалённые объекты исчезнут).
7. 1cv8 DESIGNER <ИБ> <аутентификация> /DisableStartupDialogs /DisableStartupMessages
      /Out <лог> /DumpConfigToFiles <erp-base\src\cf> -Format Hierarchical [-update]
8. update завершился кодом ≠ 0 → очистка и один повтор в режиме full.
9. Код ≠ 0 → статус error, исключение (код возврата скрипта 1).
10. git add -A src/cf; если есть изменения → commit «config: выгрузка <режим> <штамп> (<N> файлов)».
11. Записать last-dump.json (status=ok, last_ok=сейчас). Удалить логи старше 30 дней. Освободить lock.
```

Атомарность: агент видит выгрузку только через `main` после `git merge base`. Частично записанная
выгрузка в `erp-base` никогда не попадает в `main`, потому что коммит делается только после кода 0.

### 4.4. Синхронизация ИБ разработки

| Режим работы команды | Что выгружаем | Доп. шаг перед выгрузкой |
|---|---|---|
| Разработка прямо в ИБ разработки (без хранилища) | Основную конфигурацию этой ИБ | — |
| ИБ подключена к хранилищу | Основную конфигурацию ИБ | Опционально `/ConfigurationRepositoryUpdateCfg` (флаг скрипта в Ф1.1, [док]) |
| Конфигурация поставки / только `.cf` | Отдельную файловую ИБ, обновлённую `/LoadCfg` | Шаг вне пилота |

> Выгрузка снимает **сохранённую основную конфигурацию**. Несохранённые изменения в открытом
> Конфигураторе в неё не попадут. Можно ли выгружать при открытом Конфигураторе той же ИБ —
> проверяется в плане, шаг 2.5 [GO].

### 4.5. Модель веток (решает К2)

```
main ──●──────────●───────●(merge base)────●(правка агента)───●(merge base)──►
        \        /       /                                    /
base ────●──────●───────●──────────────────────────────────────●──►  (только export-config.ps1)
       init   dump1   dump2                              dump3 (уже с загруженной правкой → без конфликта)
```

- `C:\1C\erp` — основной worktree, ветка `main`. Его открывают в VS Code, в нём работает агент.
- `C:\1C\erp-base` — второй worktree, ветка `base`. Лежит **вне** открытой папки, поэтому ни VS Code,
  ни агент не видят дубликат 1–2 ГБ.
- Вливание `git merge base` — вручную или агентом по правилу (§16). Если конфликт — значит, один и тот же
  модуль изменён и в Конфигураторе, и агентом. Решает человек.

### 5.3. Файл статуса `last-dump.json` (контракт v1)

```json
{
  "schema": 1,
  "status": "ok",
  "mode": "update",
  "started": "2026-10-14T02:30:01.123+03:00",
  "finished": "2026-10-14T02:32:40.004+03:00",
  "last_ok": "2026-10-14T02:32:40.004+03:00",
  "changed_files": 7,
  "commit": "a1b2c3d",
  "log": "C:\\1C\\logs\\export-20261014-023001-update.log",
  "message": null
}
```

`status`: `ok` | `error`. При `error` поле `message` содержит текст исключения, `last_ok` берётся
из предыдущего статуса. Файл пишется PowerShell с BOM — читатель обязан открывать его как `utf-8-sig`.

### 5.4. Контракты инструментов MCP-сервера `1c-config` (API v1)

Общие правила: все инструменты read-only; ответ — JSON-объект (структурированный вывод FastMCP);
длина ответа не больше `MAX_RESPONSE_CHARS = 20000`, при обрезке ставится `"truncated": true` и
подсказка `"hint"`, как получить остаток.

| # | Инструмент | Аргументы | Результат (кратко) | Лимиты |
|---|---|---|---|---|
| 1 | `config_status` | — | конфигурация (имя, синоним, версия из `Configuration.xml`), `last-dump.json`, `age_hours`, HEAD `main`, `behind_base` (сколько коммитов `base` не влито), `dirty_files`, `api_version`, `warnings[]` | < 1 с |
| 2 | `list_objects` | `kind`, `name_filter?`, `subsystem?`, `offset=0`, `limit=100` | `total`, `items[{full_name, synonym}]` | `limit` ≤ 500 |
| 3 | `find_object` | `query`, `kinds?`, `limit=20` | совпадения по имени и синониму (подстрока, без регистра, ё=е) | ≤ 100 |
| 4 | `describe_object` | `full_name`, `sections?` (`attributes`, `tabular_sections`, `dimensions`, `resources`, `forms`, `commands`, `modules`, `register_records`, `subsystems`) | выжимка объекта (пример ниже); **не** сырой XML | 20 000 симв. |
| 5 | `list_module_methods` | `full_name`, `module` | `methods[{name, kind: Процедура/Функция, export, directive, region, params, start_line, end_line}]` | — |
| 6 | `read_module` | `full_name`, `module`, `method?`, `start_line?`, `end_line?` | `text`, `start_line`, `end_line`, `total_lines` | ≤ 400 строк за вызов |
| 7 | `search_code` | `pattern`, `regex=false`, `kinds?`, `max_hits=50` | `hits[{full_name, module, line, text}]`, `total_hits` | ≤ 200; `git grep` |
| 8 | `check_module` | `full_name`, `module` | `diagnostics[{line, severity, code, message}]`, `counts{error,warning,info}`, `bslls_version` | таймаут 90 с |

Пример `describe_object("Документ.РеализацияТоваровУслуг", sections=["attributes","tabular_sections","register_records"])`:

```json
{
  "full_name": "Документ.РеализацияТоваровУслуг",
  "synonym": "Реализация товаров и услуг",
  "source": "Documents/РеализацияТоваровУслуг.xml",
  "attributes": [
    {"name": "Контрагент", "synonym": "Контрагент", "type": ["Справочник.Контрагенты"]},
    {"name": "СуммаДокумента", "synonym": "Сумма", "type": ["Число(15,2)"]}
  ],
  "tabular_sections": [
    {"name": "Товары", "attributes": [
      {"name": "Номенклатура", "type": ["Справочник.Номенклатура"]},
      {"name": "Количество", "type": ["Число(15,3)"]}
    ]}
  ],
  "register_records": ["РегистрНакопления.ТоварыНаСкладах"],
  "truncated": false
}
```

### 5.5. Формат ошибок

Ошибка инструмента возвращается как ошибка MCP (`isError: true`, исключение `ToolError` в FastMCP),
текст которой начинается с кода:

| Код | Когда | Подсказка агенту в тексте |
|---|---|---|
| `OBJECT_NOT_FOUND` | Нет такого объекта в выгрузке | «Вызови find_object('<часть имени>')» |
| `MODULE_NOT_FOUND` | У объекта нет такого модуля | список доступных модулей объекта |
| `METHOD_NOT_FOUND` | Нет метода в модуле | «Вызови list_module_methods» |
| `BAD_ARGUMENT` | Неизвестный `kind`, неверный диапазон строк | допустимые значения |
| `PATH_REJECTED` | Путь вне `ONEC_CF_DIR` (защита) | — |
| `DUMP_MISSING` | Нет `Configuration.xml` | «Выгрузка не выполнена, запусти задачу VS Code „1С: выгрузить“» |
| `BSLLS_FAILED` | `analyze` упал или вышел по таймауту | stderr (первые 1000 символов) |

## 6. СХЕМА ХРАНИЛИЩА

СУБД не используется: источник истины — git, а индекс сервера строится в памяти.

| Хранилище | Содержимое | Обоснование |
|---|---|---|
| git, ветка `base` | Снимки выгрузки из ИБ | История и diff «что изменилось в базе за ночь» |
| git, ветка `main` | Снимок + правки агента и человека | Review изменений до переноса в ИБ |
| Индекс в памяти сервера | Список объектов из `Configuration.xml` (ChildObjects); синонимы — лениво при первом `find_object`; обратный индекс подсистем — лениво | ERP: `Configuration.xml` разбирается за 1–2 с; полный проход синонимов — 10–20 с один раз за сессию |
| Ключ инвалидации | `git rev-parse HEAD` + mtime `Configuration.xml` | Без ручного сброса кэша; учитывает и merge, и правки |

Наивный подход сначала: дискового кэша нет. Он добавляется в Ф1.1 (`%LOCALAPPDATA%\onec-config\index-<HEAD>.json`)
только если холодный `find_object` на реальной выгрузке дольше 10 с.

Настройки git для репозитория (обязательные):

| Ключ | Значение | Зачем |
|---|---|---|
| `core.longpaths` | `true` | Пути ERP > 260 символов |
| `core.quotepath` | `false` | Кириллица в выводе git без экранирования |
| `core.autocrlf` | `false` | Не трогать CRLF выгрузки |
| `feature.manyFiles` | `true` | Индекс v4 + untracked cache для ~100 тыс. файлов |
| `core.fsmonitor` | `true` (опц.) | Ускорение `git status` (Git for Windows 2.37+) |

`.gitattributes`: `* -text`, `*.bin binary`. `.gitignore`: `src/cf/ConfigDumpInfo.xml`.

## 7. АРХИТЕКТУРНЫЕ ПАТТЕРНЫ И СТИЛИ

Базовый стиль — **локальный пакетный конвейер + read-only адаптеры (MCP) над файловым снимком**.

| Паттерн | Где | Обоснование под эти условия |
|---|---|---|
| Snapshot + Git as Source of Truth | Выгрузка → `base` | Чтение без ИБ; история; при ERP-объёме инкрементальный снимок 1–3 мин |
| Two-branch reconciliation (base/main) | §4.5 | Однонаправленные потоки: выгрузка не пишет туда, где работает агент |
| Idempotent job + lock + status file | `export-config.ps1` | Три триггера могут совпасть; повтор безопасен; агент видит и неудачи |
| Ports & Adapters | `1c-config`: `layout`/`index`/`bsl`/`search`/`diagnostics` | Ошибка в карте формата правится в одном модуле |
| Lazy index + cache keyed by HEAD | `index.py` | Старт сервера мгновенный (не блокирует `initialize`), инвалидация без ручных действий |
| Progressive disclosure | `list_module_methods` → `read_module(method)`; `describe_object(sections)` | Модули ERP по 10 тыс. строк; экономия токенов DeepSeek |
| Delegation to proven engine | `check_module` → `bsl-language-server analyze` | Диагностики стандарта без своего парсера; не зависит от экспериментального MCP-режима |
| Feature toggle по Go/No-Go | `bsl-ls` в `mcp.json` (`disabled`) | Экспериментальный сервер выключается без правки кода |
| Dry-run by default | `load-changes.ps1` | Запись в ИБ — только явным `-Apply` |

Не используются (избыточно для пилота на одного): Docker, Elasticsearch, RAG/векторный поиск, HTTP-транспорт, фоновые демоны.

| Параметр | Значение |
|---|---|
| Провайдер / клиент | DeepSeek API через Zoo/Roo Code (провайдер DeepSeek) |
| Режим агента | Code (правки), Ask/Architect (вопросы); правила `.roo/rules/` действуют во всех режимах |
| Температура | 0–0.3 для правок кода (настройка профиля Roo) |

| Таймаут MCP | `timeout: 120` с для обоих серверов (у Roo по умолчанию 60) [R02] |

Системная часть промпта — файлы правил (тексты свои, лицензионно чистые):

| Файл | Содержание |
|---|---|
| `.roo/rules/00-project.md` | Что за проект, раскладка `src/cf`, модель веток, где что лежит, что такое `full_name` |
| `.roo/rules/10-mcp-tools.md` | Политика инструментов: порядок вызовов, запреты, обработка ошибок (§16, раздел «Правила агента») |

Алгоритм типового ответа агента:

1. `config_status`, если в задаче это первый вызов. Если `age_hours > 24` или `behind_base > 0`, предупредить пользователя первой строкой.
2. Найти объект: `find_object` или `list_objects`. Структура: `describe_object` с нужными `sections`.
3. Код: `list_module_methods`, затем `read_module(method=…)`. Модуль целиком не читать.
4. Вызовы и использования: `search_code`.
5. После правки `*.bsl`: `check_module`. Ошибки уровня Error исправить, остальное перечислить пользователю.

Нормы: 152-ФЗ «О персональных данных» (если live-доступ даёт данные ИБ); режим коммерческой тайны
организации (код конфигурации — объект интеллектуальной собственности). DeepSeek — внешний сервис

| Пароли 1С | Нет | Только в переменных окружения пользователя, читает только `export-config.ps1`; в `mcp.json` и git их нет |
| Макеты с возможными реальными данными (`*.bin`, `Ext/Template*`) | Нет | `.rooignore`; `1c-config` их не отдаёт |
| Логи выгрузки | Нет | `C:\1C\logs` вне репозитория |

## 12. СЦЕНАРИИ ПОТОКОВ (SEQUENCE)

### 12.1. Happy Path — вопрос по конфигурации

1. Пользователь: «Какие движения делает документ РеализацияТоваровУслуг и где они формируются?»
2. Агент → `config_status` → свежесть 6 ч, `behind_base = 0`, предупреждений нет.
3. Агент → `describe_object(…, sections=["register_records"])` → три регистра.
4. Агент → `list_module_methods(…, "Object")` → находит `ОбработкаПроведения` (строки 120–210).
5. Агент → `read_module(…, method="ОбработкаПроведения")` → 90 строк.
6. Агент отвечает со ссылками на имена регистров и строки модуля.

### 12.2. Цикл правки

1. Агент правит `src/cf/CommonModules/X/Ext/Module.bsl` в `main` (с подтверждением записи).
2. Агент → `check_module("ОбщийМодуль.X", "Module")` → 0 Error, 2 Warning → сообщает.
3. Человек делает review (`git diff`), коммитит в `main`.
4. Перенос в ИБ разработки: вручную в Конфигураторе или `load-changes.ps1 -Apply` (Ф1.5).
5. Ночная выгрузка приносит тот же текст в `base` → `git merge base` проходит без конфликта.

### 12.3. Error Path — выгрузка упала

1. 02:30: `1cv8` вернул код 1 (ИБ недоступна или неверный пароль).
2. Скрипт: статус `error`, `message`, `last_ok` прежний; коммита нет; `main` не тронут.
3. Утром агент → `config_status` → `warnings: ["Последняя выгрузка с ошибкой 2026-10-14 02:31, данные от 2026-10-13 02:33"]`.
4. Агент первой строкой сообщает пользователю и предлагает запустить задачу «1С: выгрузить» после исправления причины (лог — в поле `log`).

### 12.4. Partial Failure — инкрементальная выгрузка испорчена

1. `-update` вернул ошибку (повреждён `ConfigDumpInfo.xml` после прерванного запуска).
2. Скрипт очищает `src/cf` и повторяет в режиме `full` (25–45 мин).
3. Успех → коммит с полной картиной; удалённые в ИБ объекты корректно исчезают из git.

### 12.5. Timeout — BSL LS

1. `check_module` → `analyze` не уложился в 90 с (холодный JVM, мало памяти).
2. `BSLLS_FAILED` с первыми 1000 символами stderr. Агент сообщает, что проверка не выполнена,
   и **не заявляет**, что ошибок нет.
3. Человек увеличивает `-Xmx` в `ONEC_BSLLS_JAVA_OPTS` или таймаут.

### 12.6. Конфликт при вливании base

1. Модуль изменён и в Конфигураторе, и агентом; `git merge base` → конфликт.
2. Агент по правилу не разрешает конфликт сам: показывает обе версии и ждёт решения человека.

## 13. КОНТРОЛЬНЫЕ ТОЧКИ (ЧЕК-ЛИСТ ПРИЁМКИ)

**Выгрузка**
- [ ] Полная выгрузка из ИБ разработки скриптом завершается кодом 0, коммит в `base`.
- [ ] Повторный запуск без изменений: режим `update`, `changed_files = 0`, нового коммита нет.
- [ ] Изменение одного модуля в Конфигураторе → `update`, коммит ровно с этим файлом.
- [ ] Прерванный запуск (закрыть окно) → следующий запуск сам делает `full` и завершается успешно.
- [ ] Два одновременных запуска → второй выходит «уже идёт».
- [ ] Планировщик (или `folderOpen`) запускает выгрузку без участия человека.
- [ ] `last-dump.json` соответствует контракту §5.3 при успехе и при ошибке.

**Сервер `1c-config`**
- [ ] `--selftest` на реальной выгрузке: число объектов по видам совпадает с числом `*.xml` в каталогах видов.
- [ ] Все 8 инструментов в `tools/list`, схемы совпадают с §5.4 (`test_server_contract.py`).
- [ ] Ни один ответ не длиннее 20 000 символов; на обрезанных стоит `truncated: true`.
- [ ] Запрос с `..` или абсолютным путём → `PATH_REJECTED`.
- [ ] `check_module` возвращает те же диагностики, что панель Problems для того же файла (с точностью до контекстных).
- [ ] Производительность на реальной выгрузке: `config_status` < 1 с, `describe_object` < 1 с, `search_code` < 5 с, `check_module` < 30 с.

**Агент**
- [ ] Контрольный набор из 10 вопросов (план, шаг 6.1): не меньше 9 ответов через инструменты, вопрос-провокация с несуществующим объектом — «не найден», без выдумки.
- [ ] После правки `.bsl` агент сам вызывает `check_module`.
- [ ] Агент не правит `*.xml` и не трогает `erp-base`.

**Безопасность**
- [ ] В `mcp.json`, git и `.roo/` нет паролей (поиск по `ONEC_PASSWORD`, `/P`).
- [ ] `.rooignore` действует (агент не открывает `*.bin`).

## 16. ДИРЕКТИВЫ ДЛЯ ИИ-ИСПОЛНИТЕЛЯ

### 16.1. Реализация (для того, кто пишет код)

1. **Строго read-only.** `1c-config` не пишет ни в `ONEC_CF_DIR`, ни в git, ни в ИБ. Единственная запись — временный каталог для `check_module`, который удаляется в `finally`.
2. **Обязательно** проверять любой путь: `Path(...).resolve()` должен быть внутри `ONEC_CF_DIR` (`is_relative_to`); иначе `PATH_REJECTED`. Пути строятся только из `layout.py` и никогда не берутся из аргументов как есть.
3. **НЕ возвращать** сырой XML объектов. Только выжимка §5.4.
4. **Обязательно** ограничивать каждый ответ `MAX_RESPONSE_CHARS` и помечать `truncated`.
5. Файлы `*.bsl` и `*.xml` читать как `utf-8-sig`; `last-dump.json` — `utf-8-sig`.
6. Поиск — только `git -c core.quotepath=false grep -n -I --null --untracked` с аргументами списком (без shell); фиксированная строка по умолчанию (`-F`), регулярка — по флагу.
7. `check_module`: скопировать один файл во временный каталог с сохранением относительного пути и запустить
   `java <ONEC_BSLLS_JAVA_OPTS> -jar <jar> analyze --srcDir <tmp> --reporter json --outputDir <tmp_out> [--configuration <cfg>]`
   с таймаутом 90 с. Ключи сверить с `--help` установленной версии; разбор отчёта — в одном месте (`diagnostics.py`).
8. **НЕ блокировать** `initialize`: индекс строится лениво при первом вызове.
9. Закрепить точные версии зависимостей (`requirements.lock`); `mcp` без диапазона версий не указывать.
10. Покрыть тестами каждый модуль на синтетической выгрузке; контрактный тест сверяет имена и схемы инструментов с §5.4. Изменение контракта = новый `API_VERSION` и мажор манифеста.
11. **НЕ добавлять** инструменты записи, выполнения кода и запросов к ИБ — это Ф2 и отдельный сервер.
12. Скрипты PowerShell: `$ErrorActionPreference = 'Stop'`, `Set-StrictMode -Version Latest`, проверка `$LASTEXITCODE` после каждого внешнего вызова; stderr git **не** перенаправлять в поток при `Stop` (PowerShell 5.1 превращает его в исключение).

### 16.2. Правила агента (текст `.roo/rules/10-mcp-tools.md`)

1. Факты о конфигурации (имена объектов, реквизиты, типы, тексты) — **только** из инструментов `1c-config`. Не нашёл — так и говоришь; имена не выдумываешь.
2. Первый вызов в задаче — `config_status`. Если выгрузке больше 24 ч, последняя выгрузка с ошибкой или `behind_base > 0` — первой строкой сообщаешь пользователю.
3. Модуль целиком не читаешь: `list_module_methods`, затем `read_module(method=…)`.
4. Использования и вызовы ищешь через `search_code`, а не перебором файлов.
5. Правишь **только** `*.bsl` в `src/cf`. XML метаданных и форм (`*.xml`, `Form.xml`) не правишь. Изменения структуры (реквизиты, формы, роли) описываешь пользователю — он делает их в Конфигураторе.
6. После каждой правки `*.bsl` вызываешь `check_module`; Error исправляешь, Warning перечисляешь. Если проверка не выполнилась — так и говоришь и не утверждаешь, что ошибок нет.
7. Ветку `base` и каталог `C:\1C\erp-base` не трогаешь. `git merge base` выполняешь только с разрешения пользователя; конфликты не разрешаешь сам.
8. `load-changes.ps1 -Apply` и любые команды `1cv8` не запускаешь.
9. Для сервера `bsl-ls` сначала `register_workspace_folder` с путём `C:/1C/erp/src/cf`.

### 17.1. Способ выгрузки конфигурации

**Критерии:** Кр-1, Кр-6, Кр-3 (свежесть), формат, понятный BSL LS и нашему серверу.

| Кандидат | Вердикт |
|---|---|
| **`1cv8 DESIGNER /DumpConfigToFiles`** [R03] | **Выбран** |
| EDT + `1cedtcli` / `ring` [R03] | Ближайший соперник, отклонён |
| gitsync [R03] | Отклонён (нужен только при хранилище) |
| 1С:ГитКонвертер [R03] | Отклонён (разовая миграция истории) |
| v8unpack [R03] | Отклонён (бинарный `.cf` без платформы) |
| COM-соединение [R03] | Отклонён (не даёт полной выгрузки) |
| Режим агента конфигуратора (HTTP) [R03] | Отклонён (лишний процесс) |
| `ibcmd` [док] | Отложен (проверить на установленной версии) |

**Почему выбран пакетный Конфигуратор.** Он есть в любой установке платформы: нечего доставлять в контур и нечего администрировать (Кр-1, Кр-6). Это штатный, документированный путь с кодом возврата [R03]. Ключ `-update` даёт 1–3 минуты вместо 25–45, поэтому выгрузку можно запускать хоть при каждом открытии проекта (Кр-3). Иерархический XML — формат, который понимают BSL LS и все серверы «по выгрузке» из [R04].

**Почему не EDT.** EDT даёт текстовый формат, ещё более удобный для git, и официальный `v8-code-style`. Но это отдельная тяжёлая IDE на Eclipse, которую пришлось бы везти в контур. Импорт проекта ERP в EDT занимает часы, а команда работает в Конфигураторе. Кроме того, формат EDT отличается от выгрузки Конфигуратора, а карта `layout.py` пишется под один формат.

**Остальные:**
- gitsync нужен, только если ИБ подключена к хранилищу и важна история его версий (вопрос В-1).
- ГитКонвертер — для разовой миграции большой истории хранилища.
- v8unpack — для разбора `.cf` без платформы, а платформа у нас есть.
- COM не делает полную выгрузку [R03].
- Режим агента конфигуратора даёт то же самое, но через HTTP-процесс, который надо поднимать и держать.

**Цена выбора:** нужна учётка 1С с правом «Администрирование»; полная выгрузка 25–45 минут; при открытом Конфигураторе возможна блокировка (проверка в плане, шаг 1.5).

**Пересмотреть, если:** команда переходит на EDT (тогда `1cedtcli`); ИБ под хранилищем и нужна история его версий (тогда gitsync); `ibcmd` на установленной платформе выгружает без Конфигуратора (тогда сравнить скорость и удобство).

### 17.2. Модель хранения выгрузки и правок

**Критерии:** Кр-3 (ничего не теряется молча), Кр-6, понятная история «что сделала база, а что агент».

| Кандидат | Вердикт |
|---|---|
| **Две ветки `base`/`main` в двух worktree** | **Выбран** |
| Одна ветка + выгрузка отказывается при «грязном» дереве | Ближайший соперник, отклонён |
| Одна ветка без защиты (v1.0) | Отклонён: затирает правки (К2) |
| Выгрузка в отдельный каталог без git, агент правит копию | Отклонён: нет механизма слияния |

**Почему выбраны две ветки.** Каждый писатель пишет только в свой каталог: выгрузка — в `erp-base`, человек и агент — в `erp`. Потоки однонаправленные. Встречаются они только через `git merge` — штатную операцию git, где совпадение правок становится видимым конфликтом, а не тихой перезаписью. Worktree `erp-base` лежит вне открытой в VS Code папки, поэтому агент не видит дубликат и не путает снимок базы с рабочей копией. История честная: автор коммитов `1C export` — всегда база, все остальные — люди и агент.

**Почему не одна ветка с защитой.** Вариант проще: выгрузка проверяет `git status` и отказывается работать, если есть незакоммиченные правки. Но защищает он только от незакоммиченного. Закоммиченная правка агента, которую ещё не перенесли в ИБ, остаётся уязвимой: как только этот объект изменят в Конфигураторе, `-update` перепишет файл версией из базы, и правка исчезнет внутри коммита «выгрузка». Кроме того, `git add -A` выгрузки смешал бы в одном коммите изменения базы и чужие правки, и история перестала бы отвечать на вопрос «кто что изменил». А каждый незакоммиченный файл останавливал бы ночную выгрузку.

**Остальные:** одна ветка без защиты молча теряет правки (К2). Отдельный каталог без git требует ручного копирования и сравнения — то, что git делает сам.

**Цена выбора:** вдвое больше места на диске (+1–2 ГБ на ERP); дисциплина регулярного `merge base`; модель непривычна тому, кто не работал с worktree.

**Пересмотреть, если:** источником истины становится git, а ИБ собирается из него (Ф3, CI-сборка `/LoadConfigFromFiles`). Тогда выгрузка из ИБ вторична и ветка `base` превращается в контроль расхождений.

### 17.3. Язык скриптов автоматизации

**Критерии:** Кр-1 (ничего не доставлять), Кр-6, надёжная обработка ошибок, кириллица.

| Кандидат | Вердикт |
|---|---|
| **Windows PowerShell 5.1** | **Выбран** |
| OneScript + `v8runner` и библиотеки сообщества [R03] | Ближайший соперник, отклонён |
| `.cmd` (v1.0) | Отклонён |
| Python (в venv сервера) | Резерв |
| PowerShell 7 | Отклонён (требует установки) |

**Почему выбран PowerShell 5.1.** Он встроен в любую Windows 10/11 — ноль доставки (Кр-1). В нём есть всё, чего не хватает `.cmd`: `try/finally`, работа с JSON для `last-dump.json`, эксклюзивное открытие файла как lock, ожидание оконного `1cv8.exe` с кодом возврата и регистрация задачи Планировщика тем же языком.

**Почему не OneScript.** Это родная экосистема 1С: язык знаком 1С-разработчику, а `v8runner` уже оборачивает ключи командной строки платформы. Но это отдельный рантайм плюс пакеты из `opm`, то есть ещё одна позиция офлайн-доставки и ещё одна версия для сопровождения. Ради одного скрипта на 150 строк это не окупается.

**Остальные:** `.cmd` не умеет структурированные данные, а кириллица в нём ломается кодовой страницей. Python возможен, но тогда выгрузка зависела бы от venv сервера: сломался venv — нет выгрузки. PowerShell 7 пришлось бы устанавливать.

**Цена выбора:** известные ловушки 5.1 — BOM у файла, stderr при `Stop`, ExecutionPolicy из GPO (учтены в §16.1 и плане).

**Пересмотреть, если:** GPO запрещает `.ps1` (шаг 0.2 плана). Тогда скрипт переписывается на Python с тем же контрактом `last-dump.json`.

### 17.4. Источник знаний агента о конфигурации

**Критерии:** Кр-1, Кр-2, Кр-3, Кр-4; слой «правила» не должен зависеть от экспериментального MCP-режима BSL LS; Кр-6.

| Кандидат | Вердикт |
|---|---|
| **Свой read-only сервер `1c-config`** | **Выбран** |
| Файловые инструменты агента поверх `src/cf` | Ближайший соперник, отклонён |
| `rlm-tools-bsl` [док] | Дополнение в Ф2 |
| VendaMax / MCP_1C_modules, `mcp1c_metadata` [R04] | Отклонены (низкая зрелость) |
| Live-серверы (`1c_mcp`, `mcp-1c`, ROCTUP) [R04] | Ф2, не источник для Ф1 |

**Почему выбран свой сервер.** Только он одновременно выполняет Кр-1…Кр-4. Сервер знает карту выгрузки: «Документ.X» — это описание и до пяти модулей в разных файлах. Он отдаёт выжимку на 2–5 тыс. символов вместо сотен КБ сырого XML, а модуль — по методам. Это прямая экономия контекста (Кр-4) и защита от угадывания имён (Кр-3). `check_module` закрывает слой «правила» независимо от BSL LS MCP. Контракт инструментов наш, поэтому чужой релиз не сломает формат ответов.

**Почему не файловые инструменты агента.** Это ближайший соперник: ничего не стоит и работает уже сейчас. Но агент не знает раскладку выгрузки. Чтобы описать документ, он открывает XML целиком, модуль на 10 тыс. строк читает полностью, а синоним ищет перебором файлов. На ERP контекст заканчивается за 2–3 вопроса, после чего модель начинает угадывать имена — ровно то, от чего защищает Кр-3.

**Остальные:**
- `rlm-tools-bsl` — сильный индекс кода и графа вызовов, но метаданные не описывает. В `research/` он не проверен и находится в бета-статусе — кандидат в дополнение, если поиск на ERP окажется медленным.
- VendaMax и `mcp1c_metadata` — демонстрационные или однофункциональные [R04].
- Live-серверы меняют ИБ (ставят расширение) и отдают данные — это нарушает Кр-2 для Ф1.

**Цена выбора:** 600–900 строк своего кода и тестов, 1–2 дня разработки, сопровождение своими силами.

**Пересмотреть, если:** холодный поиск на реальной ERP дольше 5 с (добавить индекс `rlm-tools-bsl`), или в MCP BSL LS появится инструмент диагностик (упростить `check_module`).

### 17.5. Слой «правила разработки» (диагностики)

**Критерии:** агент сам видит замечания к своей правке; Кр-5 (стабильный интерфейс); Кр-1; одинаковые правила у агента и человека.

| Кандидат | Вердикт |
|---|---|
| **`check_module` → `bsl-language-server analyze`** [R06] | **Выбран** |
| `mcp-bsl-lsp-bridge` [док] | Ближайший соперник, отклонён |
| Нативный MCP-режим BSL LS [R06] | Отклонён для правил: нет инструмента диагностик |
| Только расширение VS Code | Отклонён: агент замечаний не видит |
| `v8-code-style` (EDT) [R06] | Отклонён: только в EDT |
| SonarQube + `sonar-bsl-plugin-community` [R06] | Ф3 (CI) |

**Почему выбран `analyze`.** Это режим CLI, предназначенный для CI: стабильный интерфейс, детерминированный JSON-отчёт и тот же движок со 130+ диагностиками, что в LSP [R06]. Он не зависит от экспериментальной части BSL LS. Jar уже есть в контуре для расширения VS Code, то есть ноль новой доставки (Кр-1). Общий `.bsl-language-server.json` даёт агенту и человеку одинаковые правила.

**Почему не мост.** `mcp-bsl-lsp-bridge` даёт диагностики «вживую» через постоянно запущенный LSP, без холодного старта JVM на каждый вызов. Это его реальное преимущество. Но он в бета-статусе и в `research/` не проверен (Кр-5). Это ещё один бинарник для доставки, а LSP с индексом всей ERP постоянно держит 2–4 ГБ памяти. Для пилота 5–15 секунд на проверку одного модуля — приемлемая плата за стабильность.

**Остальные:** нативный MCP-режим не публикует инструмент диагностик [R06]; расширение VS Code показывает замечания только человеку; `v8-code-style` живёт только в EDT; SonarQube — отдельный сервер, ему место в CI (Ф3).

**Цена выбора:** холодный старт JVM на каждый вызов; межмодульные диагностики при анализе одного файла могут отличаться от полного анализа.

**Пересмотреть, если:** MCP-режим BSL LS получает инструмент диагностик (переключить `check_module` на него), или холодный вызов стабильно дольше 30 с (рассмотреть мост).

### 17.6. Слой «язык» (справка по платформе)

**Критерии:** Кр-1 (без Docker), Кр-6, точность сигнатур методов платформы.

| Кандидат | Вердикт |
|---|---|
| **Знания модели + `20-bsl-standards.md` + нативный MCP BSL LS (`global_member_info`, `type_info`)** [R06] | **Выбран** |
| Синтакс-помощник на Elasticsearch (IElagin, Antonio1C, axel-avb) [R04] | Ближайший соперник, отклонён |
| ИТС (its.1c.ru) [R06] | Отклонён: подписка, не программный доступ |
| Свой поиск по `shcntx_ru.hbk` (`bsl-help-toc-parser`) [R06] | Резерв |

**Почему выбрано это сочетание.** Нативный MCP BSL LS отдаёт сведения о глобальном контексте платформы из того же jar, что уже доставлен. Это дополнение за нулевую цену: не заработает — выключаем флагом `disabled`, и ничего не ломается. Базовые знания BSL у модели есть, а правила задают стиль.

**Почему не синтакс-помощник.** Он точнее (около 23 тыс. документов справки, карточка с сигнатурой и контекстами [R04]), но требует Docker и Elasticsearch. Для изолированного контура без Docker и без прав администратора это неприемлемо (Кр-1).

**Остальные:** ИТС закрыт подпиской и не даёт программного доступа. Свой разбор `.hbk` возможен, но это отдельная разработка без доказанной необходимости.

**Цена выбора:** MCP-режим экспериментальный и требует 2–4 ГБ памяти; без него точность сигнатур — на совести модели.

**Пересмотреть, если:** на приёмке (вопрос 9) или в работе агент регулярно ошибается в сигнатурах платформы. Тогда — инструмент поиска по `shcntx_ru.hbk` внутри `1c-config`.

### 17.7. MCP-клиент в VS Code

**Критерии:** Кр-7 (конфиг в проекте), работа с DeepSeek, управление таймаутами и автоодобрением, то, что уже стоит.

| Кандидат | Вердикт |
|---|---|
| **Zoo Code / Roo Code** [R02] | **Выбран** |
| Cline [R02] | Ближайший соперник, отклонён |
| GitHub Copilot [R02] | Отклонён |
| Continue, Cody [R02] | Отклонены |
| Cursor | Вне скоупа (не VS Code) |

**Почему выбран Zoo/Roo Code.** Проектный `.roo/mcp.json` лежит в git и подхватывается каждым, кто открыл проект (Кр-7). Правила разложены по режимам (`.roo/rules/`, `.roo/rules-code/`). Есть `timeout`, `alwaysAllow`, `disabledTools` и подстановка `${env:VAR}` [R02] — всё, что нужно для схемы §14. И главное — он уже установлен и работает с DeepSeek: смена клиента — лишний риск без выигрыша.

**Почему не Cline.** У Cline самая зрелая поддержка MCP и больше всего статей сообщества 1С [R02]. Но его конфиг серверов глобальный (`cline_mcp_settings.json` в профиле VS Code) и в проект не коммитится. Для команды пришлось бы раздавать инструкцию вместо файла. Серверы при этом совместимы: переход на Cline — это перенос одного JSON-блока.

**Остальные:** Copilot требует подписки, а подключить DeepSeek в нём нельзя или неудобно; у Continue YAML-конфиг, несовместимый с остальными; у Cody MCP только в Agent mode [R02].

**Цена выбора:** Zoo — форк Roo: документация Roo может не совпадать с поведением форка.

**Пересмотреть, если:** форк перестаёт развиваться или ломает MCP. Тогда Roo Code (конфиг тот же) или Cline (перенести блок `mcpServers`).

### 17.8. Транспорт MCP

**Критерии:** Кр-6, безопасность (нет сетевой поверхности), Кр-7.

| Кандидат | Вердикт |
|---|---|
| **stdio** [R01] | **Выбран** |
| Streamable HTTP [R01] | Ближайший соперник, Ф3 |
| SSE | Отклонён (устаревающий транспорт) [R01] |

**Почему выбран stdio.** Сервер — дочерний процесс агента: нет порта, нет аутентификации, нет службы. Запуском и остановкой управляет клиент. Это минимальная поверхность атаки и ноль администрирования (Кр-6).

**Почему не Streamable HTTP.** Он позволяет держать один сервер на всю команду и одну выгрузку. Но тогда нужны аутентификация, TLS, служба Windows и открытый порт — ради одного пользователя пилота это чистые издержки.

**Цена выбора:** у каждого разработчика свои процессы и своя копия выгрузки; JVM на каждой машине.

**Пересмотреть, если:** в Ф3 три и более разработчика работают с одной выгрузкой. Тогда Streamable HTTP с OAuth2 через прокси (§1.1, строка 8).

### 17.9. Правила для агента

**Критерии:** Кр-5 (лицензия), привязка к нашим инструментам, краткость (промпт тоже тратит контекст — Кр-4).

| Кандидат | Вердикт |
|---|---|
| **Свои `.roo/rules/` (3 файла)** | **Выбран** |
| `ai_rules_1c` (comol) [док] | Ближайший соперник, Ф2 после проверки права |
| Полный текст стандартов its.1c.ru | Отклонён: объём, подписка |
| Без правил | Отклонён: агент не знает порядок инструментов |

**Почему выбраны свои.** Три коротких файла описывают то, чего не знает ни один чужой набор: порядок вызова именно наших инструментов, запрет править XML, работу с ветками. Тексты свои, поэтому лицензионный вопрос не возникает. Объём небольшой, и промпт не съедает контекст.

**Почему не `ai_rules_1c`.** Это богатый и продуманный набор, но у репозитория нет лицензии. Часть файлов содержит только заголовки (полный текст отдаётся их Docker-сервером), а субагенты и команды рассчитаны на Claude Code и Cursor, не на Roo.

**Остальные:** полный текст стандартов слишком велик для промпта и закрыт подпиской; без правил агент будет читать модули целиком и править XML.

**Цена выбора:** выжимка стандартов неполная — детальную проверку берёт на себя `check_module`.

**Пересмотреть, если:** право использования `ai_rules_1c` подтверждено. Тогда полнотекстовые файлы идут в `.roo/rules-code/` (только режим Code).

### 17.10. Модель LLM

**Критерии:** данность пилота; архитектура от модели не зависит (MCP — открытый протокол).

| Кандидат | Вердикт |
|---|---|
| **DeepSeek API** | **Выбран (данность)** |
| Локальная LLM (Ollama, vLLM) | Ближайший соперник, Ф3 / при отказе В-3 |
| Другие облачные API | Не рассматривались: вопрос утечки тот же |

**Почему DeepSeek.** Он уже используется, оплачен и доступен из контура. Пилот проверяет инструменты, а не модель, поэтому менять работающее незачем. Все компоненты общаются с моделью через клиента и MCP, так что смена модели не трогает ни сервер, ни выгрузку.

**Почему не локальная модель.** Она полностью снимает вопрос передачи кода наружу (§10). Но ей нужен GPU, а качество вызова инструментов на доступном железе обычно ниже — это риск провалить приёмку по причинам, не связанным с архитектурой.

**Цена выбора:** код и метаданные конфигурации уходят во внешний сервис (вопрос В-3).

**Пересмотреть, если:** ИБ не согласует В-3, или на приёмке модель вызывает инструменты хуже 9 из 10.

## 18. ВОПРОСЫ И ОТВЕТЫ

### 18.1. Для разработчиков

**Зачем сервер, если агент и так читает файлы в `src/cf`?**
Агент читает файлы, но не знает карту: что `Документ.X` — это `Documents/X.xml` плюс пять модулей,
что синоним «Реализация» живёт внутри XML, что модуль на 10 тыс. строк читать целиком нельзя.
Сервер — это карта, выжимки и проверка, а не дублирование чтения.

**Почему не одна ветка?**
`-update` пишет в каталог выгрузки поверх всего. Если там же правит агент, незакоммиченные правки
исчезают молча. Две ветки превращают это в видимый конфликт git.

**Что если MCP-режим BSL LS не заработает?**
Ставим `"disabled": true`. Слой «правила» остаётся (`check_module`), язык — знания модели плюс правила `20-bsl-standards.md`.

**Как быстро агент видит изменения из Конфигуратора?**
После задачи «1С: выгрузить» (1–3 мин) и `git merge base`. Без ручного запуска — к утру.

**Можно ли агенту править формы и реквизиты?**
Нет. Ручная правка XML форм и метаданных — частая причина ошибок загрузки. Агент описывает изменение, человек делает его в Конфигураторе.

**Что если Планировщик запрещён политикой?**
Работает задача VS Code `folderOpen` с `-IfOlderThanHours 12` — выгрузка при открытии проекта.

**Почему выгрузка не из рабочей базы?**
Рабочая база — продуктив. Выгрузка не меняет базу, но нагружает её и требует пароль администратора;
ИБ разработки содержит ту же конфигурацию плюс текущие доработки.
