## 0. ВВЕДЕНИЕ ДЛЯ ЧИТАТЕЛЯ

### 0.1. Какую задачу решает система

Разработчик 1С работает в редакторе VS Code вместе с AI-агентом — расширением, которое по просьбе
человека читает и изменяет код. Чтобы агент отвечал о конкретной конфигурации предприятия, а не по
общим знаниям, ему нужен доступ к её составу (справочники, документы, регистры, их реквизиты) и к
текстам модулей. Без такого доступа агент либо просит вставлять код вручную, либо называет объекты,
которых в конфигурации нет.

Система решает три задачи:

1. Ежедневно и автоматически выгружает конфигурацию из информационной базы в текстовые файлы и
   сохраняет их в git. Так у агента всегда есть свежий снимок конфигурации, а у человека — история изменений.
2. Даёт агенту набор инструментов: найти объект, получить его описание, прочитать нужную процедуру,
   найти вызовы метода, проверить изменённый модуль на соответствие стандартам разработки.
3. Ограничивает агента. Он не изменяет информационную базу и не правит описания метаданных; любые
   изменения проходят через человека.

### 0.2. Как устроено решение

1. **Выгрузка.** Скрипт `export-config.ps1` по расписанию запускает Конфигуратор в пакетном режиме
   (без окон и участия человека). Конфигуратор выгружает конфигурацию информационной базы разработки
   в XML-файлы и файлы модулей `*.bsl`. Результат сохраняется в git, в отдельной ветке `base`.
2. **Рабочая копия.** Человек и агент работают в другой ветке — `main`. Свежую выгрузку переносят в неё
   командой `git merge base`. Две ветки нужны для того, чтобы выгрузка не могла стереть правки,
   которые ещё не перенесены в базу (§4.5).
3. **Сервер `1c-config`.** Небольшая программа на Python, которую проект разрабатывает сам (фаза 2 плана).
   Агент запускает её на том же компьютере и обращается к ней по протоколу MCP. Сервер читает файлы
   рабочей копии и отвечает на запросы вида «какие реквизиты у документа», «покажи процедуру»,
   «где вызывается метод», «проверь модуль». Сервер ничего не изменяет — ни файлы, ни базу, —
   поэтому его называют сервером «только для чтения» (read-only).
4. **Проверка кода.** Для проверки модуля сервер вызывает BSL Language Server — свободно
   распространяемый анализатор кода 1С, в который встроены правила стандартов разработки.
5. **Агент и модель.** Агент (Zoo Code или Roo Code) передаёт вопрос внутренней языковой модели
   организации (OpenCoder) через адаптер с OpenAI-совместимым интерфейсом. Модель решает, какие
   инструменты вызвать, получает от сервера факты и на их основе формирует ответ. Код и описание
   конфигурации за пределы организации не передаются.

| ИБ разработки | База, в которой разработчик вносит изменения в конфигурацию. Это не рабочая база, с которой работают пользователи. |
| Конфигурация, метаданные | Прикладное решение (например, ERP): состав объектов (справочники, документы, регистры), их реквизиты, формы и модули. Описание этого состава называют метаданными. |

| Выгрузка конфигурации | Сохранение конфигурации в каталог в виде XML-файлов (описания объектов) и `*.bsl` (тексты модулей). Инкрементальная выгрузка (ключ `-update`) записывает только изменённые объекты. |
| git, коммит, ветка | git — система контроля версий. Коммит — сохранённое состояние файлов с описанием. Ветка — независимая линия коммитов. |

| AI-агент | Расширение VS Code (здесь Zoo Code или Roo Code), которое по просьбе человека выполняет задачи: читает и правит файлы, вызывает инструменты, запускает команды с подтверждения. |

## 1. АРХИТЕКТУРНЫЙ МАНИФЕСТ

**Схема компонентов:**

```
ИБ разработки ──1cv8 DESIGNER /DumpConfigToFiles──► git: ветка base (worktree erp-base)
   ▲                                                      │ git merge base
   │ (ручной, -Apply) load-changes.ps1                    ▼
   └──────────────────────────────────────────── git: ветка main (worktree erp) ◄── правки агента (*.bsl)
                                                          │ читают
                    ┌─────────────────────────────────────┼──────────────────────────┐
                    ▼                                     ▼                          ▼
          MCP «1c-config» (Python, stdio)      MCP «bsl-ls» (Java, stdio)   VS Code + Language 1C (BSL)
          метаданные, код, поиск,              type_info, global_member_*   подсветка, Problems
          check_module (BSL LS analyze)        (экспериментальный)
                    └──────────────┬──────────────────────┘
                                   ▼
                     Zoo Code / Roo Code (MCP-клиент) ──► адаптер 127.0.0.1:8787 ──► внутренняя LLM (OpenCoder)
```

**Как читать схему.** Верхняя часть — движение конфигурации. Скрипт выгружает её из ИБ разработки
в ветку `base`; человек переносит выгрузку в рабочую ветку `main`; правки агента попадают обратно в ИБ
только через человека (вручную или скриптом `load-changes.ps1` с явным ключом `-Apply`). Нижняя часть —
кто читает рабочую копию: сервер `1c-config`, встроенный MCP-режим BSL LS и расширение VS Code для
подсветки кода. Агент получает ответы обоих серверов и через адаптер передаёт их внутренней модели.

**Главная идея решения.** Все три вида знаний, которые нужны агенту, — состав конфигурации, язык BSL
и правила разработки — агент получает через один сервер `1c-config`, который разрабатывается в рамках
проекта. Сервер работает только на чтение: он не изменяет ни файлы, ни базу.

Так сделано по двум причинам:
- Сторонние серверы для 1С различаются по зрелости и могут меняться без предупреждения. Собственный
  сервер даёт стабильный, проверенный тестами набор инструментов, а ответы рассчитаны на ограниченный
  контекст модели.
- Встроенный MCP-режим BSL LS пока экспериментальный и не выдаёт замечания к коду (§17.5). Поэтому
  проверку кода выполняет наш сервер: он вызывает BSL LS в режиме пакетной проверки `analyze`.

Встроенный MCP-режим BSL LS подключается дополнительно, для справки по встроенным функциям платформы.
Если он не пройдёт проверку при развёртывании (план, шаг 4.3), его отключают одной настройкой;
остальная система продолжает работать.

## 2. НАЗНАЧЕНИЕ И ОХВАТ ДОКУМЕНТА

**Цель:** дать AI-агенту в VS Code достоверный и структурированный доступ к конфигурации 1С
(метаданные и код), к языку BSL и к правилам разработки. Агент читает не базу, а выгрузку
конфигурации, сохранённую в git; для чтения база не нужна. Документа достаточно, чтобы разработчик
или другая ИИ-система реализовали решение без дополнительных вопросов; решения по вопросам В-1…В-6 собраны в §18.2.

**Охват:**

| Компонент | Фаза | Статус |
|---|---|---|
| Конвейер выгрузки `export-config.ps1` + расписание | Ф1 | ядро |
| Модель веток `base`/`main` | Ф1 | ядро |
| MCP-сервер `1c-config` (свой, Python) | Ф1 | ядро |
| BSL LS: `analyze` (через `1c-config`) + нативный MCP | Ф1 | ядро / дополнение [GO] |
| Правила агента `.roo/rules/` (свои тексты) | Ф1 | ядро |
| Обратный контур `load-changes.ps1` (частичная загрузка в ИБ разработки) | после пилота | в пилоте правки переносятся вручную (решение В-5) |
| Live-доступ к копии ИБ (выбор сервера — §17.11) | Ф2 | расширение |
| `rlm-tools-bsl`, `ai_rules_1c` | Ф2 | расширение |
| Команда: CI-анализ, общий конфиг, OAuth2 | Ф3 | развитие |

**Вне охвата:** запись в рабочую ИБ; автоматическая загрузка без человека; локальная LLM
(упомянута как альтернатива в §17); EDT-контур.

## 4. ПОДСИСТЕМА ВЫГРУЗКИ

### 4.1. Тип и режим запуска

Скрипт `scripts/export-config.ps1` (PowerShell 5.1, файл в UTF-8 **с BOM**), версия 1.0.
Запускается тремя способами, все идемпотентны:

| Триггер | Команда | Назначение |
|---|---|---|
| Планировщик Windows, 02:30, `StartWhenAvailable`, `IgnoreNew` | `export-config.ps1` | Ежедневный снимок конфигурации |
| Задача VS Code `runOn: folderOpen` | `export-config.ps1 -IfOlderThanHours 12` | Свежесть, если ПК ночью выключен или Планировщик запрещён политикой |
| Задача VS Code вручную | `export-config.ps1` / `-Full` | По требованию |

### 4.2. Механизм отслеживания изменений (watermark)

- Платформенный: `ConfigDumpInfo.xml` в каталоге выгрузки. При наличии — `-update` (выгружаются только
  изменённые объекты); при отсутствии — полная выгрузка. Файл исключён из git (`.gitignore`) и хранится только в рабочей копии `erp-base`.
- Логический: `last-dump.json` в `C:\1C\logs` — пишется **при каждом запуске**, в том числе при ошибке;
  поле `last_ok` переносится из прошлого статуса, если текущий запуск упал.
- git: коммит в `base` создаётся, только если есть изменения; автор `1C export <export@localhost>` —
  отличается от человека и агента.

### 4.3. Алгоритм

```text
1. Если задан -IfOlderThanHours N и last_ok моложе N часов → выход 0 («свежая»).
2. Захватить lock-файл logs\export.lock (эксклюзивное открытие). Занят → выход 0 («уже идёт»).
3. Проверить переменные: ONEC_BIN, ONEC_IB_PATH | ONEC_IB_SERVER; опц. ONEC_USER/ONEC_PASSWORD.
4. Если в erp-base есть незакоммиченные изменения в src/cf (след прерванного запуска):
      git reset --hard; git clean -fdx src/cf; режим := full.
   (worktree base принадлежит только скрипту — откат безопасен.)
5. Режим := full, если -Full или нет ConfigDumpInfo.xml; иначе update.
6. full: очистить src/cf через git rm + git clean (корректно с длинными путями, удалённые объекты исчезнут).
7. 1cv8 DESIGNER <ИБ> <аутентификация> /DisableStartupDialogs /DisableStartupMessages
      /Out <лог> /DumpConfigToFiles <erp-base\src\cf> -Format Hierarchical [-update]
8. update завершился кодом ≠ 0 → очистка и один повтор в режиме full.
9. Код ≠ 0 → статус error, исключение (код возврата скрипта 1).
10. git add -A src/cf; если есть изменения → commit «config: выгрузка <режим> <штамп> (<N> файлов)».
11. Записать last-dump.json (status=ok, last_ok=сейчас). Удалить логи старше 30 дней. Освободить lock.
```

Атомарность: агент видит выгрузку только через `main` после `git merge base`. Частично записанная
выгрузка в `erp-base` никогда не попадает в `main`, потому что коммит делается только после кода 0.

### 4.4. Синхронизация ИБ разработки

ИБ разработки подключена к хранилищу конфигурации (решение В-1). Принятый порядок:

- Скрипт выгружает основную конфигурацию ИБ разработки **как есть** и **не обновляет** её из хранилища.
  Скрипт ничего не изменяет в базе, а агент видит то же, что разработчик в Конфигураторе, включая
  захваченные и ещё не помещённые в хранилище изменения.
- Изменения, которые коллеги поместили в хранилище, агент увидит после того, как разработчик сам
  обновит свою конфигурацию из хранилища и пройдёт очередная выгрузка.
- Перенос правок агента в ИБ (в пилоте — вручную, позже — скриптом `load-changes.ps1`) возможен только
  для объектов, захваченных разработчиком в хранилище.

| Альтернатива | Почему не выбрана |
|---|---|
| Обновлять ИБ из хранилища перед каждой выгрузкой (`/ConfigurationRepositoryUpdateCfg`) | Скрипт каждую ночь изменял бы базу разработчика и мог вмешаться в работу с захваченными объектами |
| Отдельная «зеркальная» ИБ, обновляемая только из хранилища | Агент не видел бы текущих изменений разработчика; ещё одна база для сопровождения |

> Выгрузка снимает **сохранённую основную конфигурацию**. Несохранённые изменения в открытом
> Конфигураторе в неё не попадут. Можно ли выгружать при открытом Конфигураторе той же ИБ —
> проверяется в плане, шаг 1.5 [GO].

### 4.5. Модель веток (решает К2)

```
main ──●──────────●───────●(merge base)────●(правка агента)───●(merge base)──►
        \        /       /                                    /
base ────●──────●───────●──────────────────────────────────────●──►  (только export-config.ps1)
       init   dump1   dump2                              dump3 (уже с загруженной правкой → без конфликта)
```

- `C:\1C\erp` — основной worktree, ветка `main`. Его открывают в VS Code, в нём работает агент.
- `C:\1C\erp-base` — второй worktree, ветка `base`. Лежит **вне** открытой папки, поэтому ни VS Code,
  ни агент не видят дубликат 1–2 ГБ.
- Перенос выгрузки в `main` (`git merge base`) выполняет человек или агент с разрешения человека (§16.2).
  Конфликт слияния означает, что один и тот же модуль изменили и в Конфигураторе, и в `main`.
  Какую версию оставить, решает человек.

### 5.5. Формат ошибок

Ошибка инструмента возвращается как ошибка MCP (`isError: true`, исключение `ToolError` в FastMCP),
текст которой начинается с кода:

| Код | Когда | Подсказка агенту в тексте |
|---|---|---|
| `OBJECT_NOT_FOUND` | Нет такого объекта в выгрузке | «Вызови find_object('<часть имени>')» |
| `MODULE_NOT_FOUND` | У объекта нет такого модуля | список доступных модулей объекта |
| `METHOD_NOT_FOUND` | Нет метода в модуле | «Вызови list_module_methods» |
| `BAD_ARGUMENT` | Неизвестный `kind`, неверный диапазон строк | допустимые значения |
| `PATH_REJECTED` | Путь вне `ONEC_CF_DIR` (защита) | — |
| `DUMP_MISSING` | Нет `Configuration.xml` | «Выгрузка не выполнена, запусти задачу VS Code „1С: выгрузить“» |
| `BSLLS_FAILED` | `analyze` упал или вышел по таймауту | stderr (первые 1000 символов) |

## 6. СХЕМА ХРАНИЛИЩА

СУБД не используется: источник истины — git, а индекс сервера строится в памяти.

| Хранилище | Содержимое | Обоснование |
|---|---|---|
| git, ветка `base` | Снимки выгрузки из ИБ | История и diff «что изменилось в базе за ночь» |
| git, ветка `main` | Снимок + правки агента и человека | Review изменений до переноса в ИБ |
| Индекс в памяти сервера | Список объектов из `Configuration.xml` (ChildObjects); синонимы — лениво при первом `find_object`; обратный индекс подсистем — лениво | ERP: `Configuration.xml` разбирается за 1–2 с; полный проход синонимов — 10–20 с один раз за сессию |
| Когда индекс строится заново | При смене текущего коммита (`git rev-parse HEAD`) или времени изменения `Configuration.xml` | Кэш не нужно сбрасывать вручную; учитываются и слияния, и правки |

На первом этапе индекс хранится только в памяти. Сохранение индекса на диск
(`%LOCALAPPDATA%\onec-config\index-<HEAD>.json`) добавляется в Ф1.1, только если первый после запуска
сервера вызов `find_object` на реальной выгрузке занимает больше 10 с.

Настройки git для репозитория (обязательные):

| Ключ | Значение | Зачем |
|---|---|---|
| `core.longpaths` | `true` | Пути ERP > 260 символов |
| `core.quotepath` | `false` | Кириллица в выводе git без экранирования |
| `core.autocrlf` | `false` | Не трогать CRLF выгрузки |
| `feature.manyFiles` | `true` | Индекс v4 + untracked cache для ~100 тыс. файлов |
| `core.fsmonitor` | `true` (опц.) | Ускорение `git status` (Git for Windows 2.37+) |

`.gitattributes`: `* -text`, `*.bin binary`. `.gitignore`: `src/cf/ConfigDumpInfo.xml`.

## 7. АРХИТЕКТУРНЫЕ ПАТТЕРНЫ И СТИЛИ

Базовый стиль — **локальный конвейер**: скрипт по расписанию сохраняет снимок конфигурации в файлы, а MCP-серверы только читают этот снимок и отдают агенту нужные части.

| Паттерн | Где | Обоснование под эти условия |
|---|---|---|
| Снимок в git как источник истины (snapshot) | Выгрузка → `base` | Чтение без ИБ; история; при ERP-объёме инкрементальный снимок 1–3 мин |
| Две ветки со слиянием (base/main) | §4.5 | Однонаправленные потоки: выгрузка не пишет туда, где работает агент |
| Повторяемая задача с блокировкой и файлом статуса (idempotent job) | `export-config.ps1` | Три триггера могут совпасть; повтор безопасен; агент видит и неудачи |
| Порты и адаптеры: формат выгрузки изолирован в отдельных модулях (ports & adapters) | `1c-config`: `layout`/`index`/`bsl`/`search`/`diagnostics` | Ошибка в карте формата правится в одном модуле |
| Отложенное построение индекса с кэшем по коммиту (lazy index) | `index.py` | Сервер запускается сразу (не задерживает подключение агента); индекс обновляется без ручных действий |
| Постепенное раскрытие: сначала перечень, потом нужная часть (progressive disclosure) | `list_module_methods` → `read_module(method)`; `describe_object(sections)` | Модули ERP по 10 тыс. строк; экономия контекста модели |
| Делегирование зрелому инструменту | `check_module` → `bsl-language-server analyze` | Диагностики стандарта без своего парсера; не зависит от экспериментального MCP-режима |
| Отключаемый компонент по итогам Go/No-Go (feature toggle) | `bsl-ls` в `mcp.json` (`disabled`) | Экспериментальный сервер выключается без правки кода |
| Пробный запуск по умолчанию (dry-run) | `load-changes.ps1` | Запись в ИБ — только явным `-Apply` |

## 12. СЦЕНАРИИ ПОТОКОВ (SEQUENCE)

### 12.1. Основной сценарий — вопрос по конфигурации

1. Пользователь: «Какие движения делает документ РеализацияТоваровУслуг и где они формируются?»
2. Агент → `config_status` → свежесть 6 ч, `behind_base = 0`, предупреждений нет.
3. Агент → `describe_object(…, sections=["register_records"])` → три регистра.
4. Агент → `list_module_methods(…, "Object")` → находит `ОбработкаПроведения` (строки 120–210).
5. Агент → `read_module(…, method="ОбработкаПроведения")` → 90 строк.
6. Агент отвечает со ссылками на имена регистров и строки модуля.

### 12.2. Цикл правки

1. Агент правит `src/cf/CommonModules/X/Ext/Module.bsl` в `main` (с подтверждением записи).
2. Агент → `check_module("ОбщийМодуль.X", "Module")` → 0 Error, 2 Warning → сообщает.
3. Человек делает review (`git diff`), коммитит в `main`.
4. Перенос в ИБ разработки: в пилоте — вручную в Конфигураторе; после пилота — `load-changes.ps1 -Apply`. Объект должен быть захвачен в хранилище.
5. Ночная выгрузка приносит тот же текст в `base` → `git merge base` проходит без конфликта.

### 12.3. Ошибка — выгрузка не выполнилась

1. 02:30: `1cv8` вернул код 1 (ИБ недоступна или неверный пароль).
2. Скрипт: статус `error`, `message`, `last_ok` прежний; коммита нет; `main` не тронут.
3. Утром агент → `config_status` → `warnings: ["Последняя выгрузка с ошибкой 2026-10-14 02:31, данные от 2026-10-13 02:33"]`.
4. Агент первой строкой сообщает пользователю и предлагает запустить задачу «1С: выгрузить» после исправления причины (лог — в поле `log`).

### 12.4. Частичный сбой — повреждена инкрементальная выгрузка

1. `-update` вернул ошибку (повреждён `ConfigDumpInfo.xml` после прерванного запуска).
2. Скрипт очищает `src/cf` и повторяет в режиме `full` (25–45 мин).
3. Успех → коммит с полной выгрузкой; удалённые в ИБ объекты корректно исчезают из git.

### 12.5. Превышено время ожидания — проверка кода

1. `check_module` → `analyze` не уложился в 90 с (первый запуск Java занимает время, или ей не хватает памяти).
2. `BSLLS_FAILED` с первыми 1000 символами stderr. Агент сообщает, что проверка не выполнена,
   и **не заявляет**, что ошибок нет.
3. Человек увеличивает `-Xmx` в `ONEC_BSLLS_JAVA_OPTS` или таймаут.

### 12.6. Конфликт при вливании base

1. Модуль изменён и в Конфигураторе, и агентом; `git merge base` → конфликт.
2. Согласно правилам (§16.2), агент не разрешает конфликт сам: показывает обе версии и ждёт решения человека.

## 16. ДИРЕКТИВЫ ДЛЯ ИИ-ИСПОЛНИТЕЛЯ

### 16.1. Реализация (для того, кто пишет код)

1. **Строго read-only.** `1c-config` не пишет ни в `ONEC_CF_DIR`, ни в git, ни в ИБ. Единственная запись — временный каталог для `check_module`, который удаляется в `finally`.
2. **Обязательно** проверять любой путь: `Path(...).resolve()` должен быть внутри `ONEC_CF_DIR` (`is_relative_to`); иначе `PATH_REJECTED`. Пути строятся только из `layout.py` и никогда не берутся из аргументов как есть.
3. **НЕ возвращать** сырой XML объектов. Только выжимка §5.4.
4. **Обязательно** ограничивать каждый ответ `MAX_RESPONSE_CHARS` и помечать `truncated`.
5. Файлы `*.bsl` и `*.xml` читать как `utf-8-sig`; `last-dump.json` — `utf-8-sig`.
6. Поиск — только `git -c core.quotepath=false grep -n -I --null --untracked` с аргументами списком (без shell); фиксированная строка по умолчанию (`-F`), регулярка — по флагу.
7. `check_module`: скопировать один файл во временный каталог с сохранением относительного пути и запустить
   `java <ONEC_BSLLS_JAVA_OPTS> -jar <jar> analyze --srcDir <tmp> --reporter json --outputDir <tmp_out> [--configuration <cfg>]`
   с таймаутом 90 с. Ключи сверить с `--help` установленной версии; разбор отчёта — в одном месте (`diagnostics.py`).
8. **НЕ блокировать** `initialize`: индекс строится лениво при первом вызове.
9. Закрепить точные версии зависимостей (`requirements.lock`); `mcp` без диапазона версий не указывать.
10. Покрыть тестами каждый модуль на синтетической выгрузке; контрактный тест сверяет имена и схемы инструментов с §5.4. Изменение контракта = новый `API_VERSION` и мажор манифеста.
11. **НЕ добавлять** инструменты записи, выполнения кода и запросов к ИБ — это Ф2 и отдельный сервер.
12. Скрипты PowerShell: `$ErrorActionPreference = 'Stop'`, `Set-StrictMode -Version Latest`, проверка `$LASTEXITCODE` после каждого внешнего вызова; stderr git **не** перенаправлять в поток при `Stop` (PowerShell 5.1 превращает его в исключение).

### 16.2. Правила агента (текст `.roo/rules/10-mcp-tools.md`)

1. Факты о конфигурации (имена объектов, реквизиты, типы, тексты) — **только** из инструментов `1c-config`. Не нашёл — так и говоришь; имена не выдумываешь.
2. Первый вызов в задаче — `config_status`. Если выгрузке больше 24 ч, последняя выгрузка с ошибкой или `behind_base > 0` — первой строкой сообщаешь пользователю.
3. Модуль целиком не читаешь: `list_module_methods`, затем `read_module(method=…)`.
4. Использования и вызовы ищешь через `search_code`, а не перебором файлов.
5. Правишь **только** `*.bsl` в `src/cf`. XML метаданных и форм (`*.xml`, `Form.xml`) не правишь. Изменения структуры (реквизиты, формы, роли) описываешь пользователю — он делает их в Конфигураторе.
6. После каждой правки `*.bsl` вызываешь `check_module`; Error исправляешь, Warning перечисляешь. Если проверка не выполнилась — так и говоришь и не утверждаешь, что ошибок нет.
7. Ветку `base` и каталог `C:\1C\erp-base` не трогаешь. `git merge base` выполняешь только с разрешения пользователя; конфликты не разрешаешь сам.
8. `load-changes.ps1 -Apply` и любые команды `1cv8` не запускаешь.
9. Для сервера `bsl-ls` сначала `register_workspace_folder` с путём `C:/1C/erp/src/cf`.

### 17.1. Способ выгрузки конфигурации

**Критерии:** Кр-1, Кр-6, Кр-3 (свежесть), формат, понятный BSL LS и нашему серверу.

| Кандидат | Вердикт |
|---|---|
| **`1cv8 DESIGNER /DumpConfigToFiles`** [R03] | **Выбран** |
| EDT + `1cedtcli` / `ring` [R03] | Ближайший соперник, отклонён |
| gitsync [R03] | Отклонён (нужен только при хранилище) |
| 1С:ГитКонвертер [R03] | Отклонён (разовая миграция истории) |
| v8unpack [R03] | Отклонён (бинарный `.cf` без платформы) |
| COM-соединение [R03] | Отклонён (не даёт полной выгрузки) |
| Режим агента конфигуратора (HTTP) [R03] | Отклонён (лишний процесс) |
| `ibcmd` [док] | Отложен (проверить на установленной версии) |

**Почему выбран пакетный Конфигуратор.** Конфигуратор входит в любую установку платформы, поэтому во внутренний контур ничего не нужно переносить и отдельно сопровождать (Кр-1, Кр-6). Это штатный и документированный способ, который возвращает код завершения [R03]. Инкрементальная выгрузка (`-update`) занимает 1–3 минуты вместо 25–45, поэтому её можно запускать даже при каждом открытии проекта (Кр-3). Иерархический XML — формат, который понимают BSL LS и все серверы, работающие с выгрузкой [R04].

**Почему не EDT.** EDT даёт текстовый формат, ещё более удобный для git, и официальный `v8-code-style`. Однако это отдельная крупная среда разработки на платформе Eclipse, которую пришлось бы переносить во внутренний контур. Импорт проекта ERP в EDT занимает часы, а команда работает в Конфигураторе. Кроме того, формат EDT отличается от выгрузки Конфигуратора, а карта `layout.py` пишется под один формат.

**Остальные:**
- gitsync нужен, только если ИБ подключена к хранилищу и важна история его версий (вопрос В-1).
- ГитКонвертер — для разовой миграции большой истории хранилища.
- v8unpack — для разбора `.cf` без платформы, а платформа у нас есть.
- COM не делает полную выгрузку [R03].
- Режим агента конфигуратора даёт то же самое, но через HTTP-процесс, который надо поднимать и держать.

**Цена выбора:** нужна учётка 1С с правом «Администрирование»; полная выгрузка 25–45 минут; при открытом Конфигураторе возможна блокировка (проверка в плане, шаг 1.5).

**Пересмотреть, если:** команда переходит на EDT (тогда `1cedtcli`); ИБ под хранилищем и нужна история его версий (тогда gitsync); `ibcmd` на установленной платформе выгружает без Конфигуратора (тогда сравнить скорость и удобство).

### 17.2. Модель хранения выгрузки и правок

**Критерии:** Кр-3 (ничего не теряется молча), Кр-6, понятная история «что сделала база, а что агент».

| Кандидат | Вердикт |
|---|---|
| **Две ветки `base`/`main` в двух worktree** | **Выбран** |
| Одна ветка + выгрузка отказывается при «грязном» дереве | Ближайший соперник, отклонён |
| Одна ветка без защиты (v1.0) | Отклонён: перезаписывает правки (К2) |
| Выгрузка в отдельный каталог без git, агент правит копию | Отклонён: нет механизма слияния |

**Почему выбраны две ветки.** Каждый писатель пишет только в свой каталог: выгрузка — в `erp-base`, человек и агент — в `erp`. Потоки однонаправленные. Встречаются они только через `git merge` — штатную операцию git, где совпадение правок становится видимым конфликтом, а не тихой перезаписью. Worktree `erp-base` лежит вне открытой в VS Code папки, поэтому агент не видит дубликат и не путает снимок базы с рабочей копией. История честная: автор коммитов `1C export` — всегда база, все остальные — люди и агент.

**Почему не одна ветка с защитой.** Вариант проще: выгрузка проверяет `git status` и отказывается работать, если есть незакоммиченные правки. Но защищает он только от незакоммиченного. Закоммиченная правка агента, которую ещё не перенесли в ИБ, остаётся уязвимой: как только этот объект изменят в Конфигураторе, `-update` перепишет файл версией из базы, и правка исчезнет внутри коммита «выгрузка». Кроме того, `git add -A` выгрузки смешал бы в одном коммите изменения базы и чужие правки, и история перестала бы отвечать на вопрос «кто что изменил». А каждый незакоммиченный файл останавливал бы ночную выгрузку.

**Остальные:** одна ветка без защиты молча теряет правки (К2). Отдельный каталог без git требует ручного копирования и сравнения — то, что git делает сам.

**Цена выбора:** вдвое больше места на диске (+1–2 ГБ на ERP); дисциплина регулярного `merge base`; модель непривычна тому, кто не работал с worktree.

**Пересмотреть, если:** источником истины становится git, а ИБ собирается из него (Ф3, CI-сборка `/LoadConfigFromFiles`). Тогда выгрузка из ИБ вторична и ветка `base` превращается в контроль расхождений.

### 17.3. Язык скриптов автоматизации

**Критерии:** Кр-1 (ничего не доставлять), Кр-6, надёжная обработка ошибок, кириллица.

| Кандидат | Вердикт |
|---|---|
| **Windows PowerShell 5.1** | **Выбран** |
| OneScript + `v8runner` и библиотеки сообщества [R03] | Ближайший соперник, отклонён |
| `.cmd` (v1.0) | Отклонён |
| Python (в venv сервера) | Резерв |
| PowerShell 7 | Отклонён (требует установки) |

**Почему выбран PowerShell 5.1.** Он встроен в Windows 10/11, его не нужно устанавливать и переносить в контур (Кр-1). В нём есть то, чего не хватает `.cmd`: обработка ошибок (`try/finally`), работа с JSON для `last-dump.json`, блокировка от параллельного запуска, ожидание завершения `1cv8.exe` с получением кода возврата и регистрация задачи в Планировщике.

**Почему не OneScript.** OneScript — инструмент из экосистемы 1С: его язык знаком разработчику 1С, а библиотека `v8runner` уже умеет вызывать Конфигуратор из командной строки. Однако OneScript требует отдельной среды выполнения и пакетов из менеджера `opm`, то есть ещё одной позиции в офлайн-наборе и ещё одной версии для сопровождения. Для одного скрипта примерно на 150 строк это неоправданно.

**Остальные:** `.cmd` не умеет структурированные данные, а кириллица в нём ломается кодовой страницей. Python возможен, но тогда выгрузка зависела бы от venv сервера: сломался venv — нет выгрузки. PowerShell 7 пришлось бы устанавливать.

**Цена выбора:** известные ловушки 5.1 — BOM у файла, stderr при `Stop`, ExecutionPolicy из GPO (учтены в §16.1 и плане).

**Пересмотреть, если:** GPO запрещает `.ps1` (шаг 0.2 плана). Тогда скрипт переписывается на Python с тем же контрактом `last-dump.json`.

### 17.4. Источник знаний агента о конфигурации

**Критерии:** Кр-1, Кр-2, Кр-3, Кр-4; слой «правила» не должен зависеть от экспериментального MCP-режима BSL LS; Кр-6.

| Кандидат | Вердикт |
|---|---|
| **Свой read-only сервер `1c-config`** | **Выбран** |
| Файловые инструменты агента (чтение файлов `src/cf` напрямую) | Ближайший соперник, отклонён |
| `rlm-tools-bsl` [док] | Дополнение в Ф2 |
| VendaMax / MCP_1C_modules, `mcp1c_metadata` [R04] | Отклонены (низкая зрелость) |
| Live-серверы (`1c_mcp`, `mcp-1c`, ROCTUP) [R04] | Ф2, не источник для Ф1 |

**Почему выбран свой сервер.** Только он одновременно выполняет Кр-1…Кр-4. Сервер знает, как устроена выгрузка: объект «Документ.X» — это файл описания и до пяти модулей в разных каталогах. Вместо исходного XML объёмом в сотни килобайт сервер отдаёт краткое описание на 2–5 тыс. символов, а модуль — по отдельным процедурам. Это экономит контекст модели (Кр-4) и не даёт ей подставлять несуществующие имена (Кр-3). Инструмент `check_module` обеспечивает проверку кода независимо от встроенного MCP-режима BSL LS. Набор и формат инструментов определяет проект, поэтому обновление стороннего компонента их не изменит.

**Почему не файловые инструменты агента.** Это ближайший соперник: он не требует разработки и доступен уже сейчас. Однако агент не знает, как устроена выгрузка. Чтобы описать документ, он открывает XML-файл целиком, модуль на 10 тыс. строк читает полностью, а синоним ищет перебором файлов. На конфигурации класса ERP контекст модели заполняется за 2–3 вопроса, после чего модель начинает подставлять имена по догадке — именно этого не допускает критерий Кр-3.

**Остальные:**
- `rlm-tools-bsl` — сильный индекс кода и графа вызовов, но метаданные не описывает. В `research/` он не проверен и находится в бета-статусе — кандидат в дополнение, если поиск на ERP окажется медленным.
- VendaMax и `mcp1c_metadata` — демонстрационные или однофункциональные [R04].
- Live-серверы меняют ИБ (ставят расширение) и отдают данные — это нарушает Кр-2 для Ф1.

**Цена выбора:** 600–900 строк своего кода и тестов, 1–2 дня разработки, сопровождение своими силами.

**Пересмотреть, если:** первый поиск после запуска сервера на реальной конфигурации ERP занимает больше 5 с (добавить индекс `rlm-tools-bsl`), или в MCP BSL LS появится инструмент диагностик (упростить `check_module`).

### 17.5. Слой «правила разработки» (диагностики)

**Критерии:** агент сам видит замечания к своей правке; Кр-5 (стабильный интерфейс); Кр-1; одинаковые правила у агента и человека.

| Кандидат | Вердикт |
|---|---|
| **`check_module` → `bsl-language-server analyze`** [R06] | **Выбран** |
| `mcp-bsl-lsp-bridge` [док] | Ближайший соперник, отклонён |
| Нативный MCP-режим BSL LS [R06] | Отклонён для правил: нет инструмента диагностик |
| Только расширение VS Code | Отклонён: агент замечаний не видит |
| `v8-code-style` (EDT) [R06] | Отклонён: только в EDT |
| SonarQube + `sonar-bsl-plugin-community` [R06] | Ф3 (CI) |

**Почему выбран `analyze`.** Это режим командной строки, предназначенный для автоматических проверок: он стабилен, выдаёт предсказуемый отчёт в JSON и использует тот же набор из 130+ диагностик, что и редактор [R06]. Он не зависит от экспериментальной части BSL LS. Файл BSL LS уже переносится в контур для расширения VS Code, поэтому дополнительной доставки не требуется (Кр-1). Общий файл настроек `.bsl-language-server.json` даёт агенту и человеку одинаковые правила.

**Почему не мост.** `mcp-bsl-lsp-bridge` получает диагностики от постоянно запущенного BSL LS, поэтому не тратит время на запуск Java при каждой проверке. Это его реальное преимущество. Однако мост находится в стадии бета-версии и в базе знаний не проверен (Кр-5). Это ещё одна программа для переноса в контур, а постоянно запущенный BSL LS с индексом всей ERP занимает 2–4 ГБ памяти. Для пилота 5–15 секунд на проверку одного модуля — приемлемая цена стабильности.

**Остальные:** нативный MCP-режим не публикует инструмент диагностик [R06]; расширение VS Code показывает замечания только человеку; `v8-code-style` живёт только в EDT; SonarQube — отдельный сервер, ему место в CI (Ф3).

**Цена выбора:** запуск Java при каждой проверке (несколько секунд); межмодульные диагностики при анализе одного файла могут отличаться от полного анализа.

**Пересмотреть, если:** MCP-режим BSL LS получает инструмент диагностик (переключить `check_module` на него), или проверка одного модуля стабильно занимает больше 30 с (рассмотреть мост).

### 17.6. Слой «язык» (справка по платформе)

**Критерии:** Кр-1 (без Docker), Кр-6, точность сигнатур методов платформы.

| Кандидат | Вердикт |
|---|---|
| **Знания модели + `20-bsl-standards.md` + нативный MCP BSL LS (`global_member_info`, `type_info`)** [R06] | **Выбран** |
| Синтакс-помощник на Elasticsearch (IElagin, Antonio1C, axel-avb) [R04] | Ближайший соперник, отклонён |
| ИТС (its.1c.ru) [R06] | Отклонён: подписка, не программный доступ |
| Свой поиск по `shcntx_ru.hbk` (`bsl-help-toc-parser`) [R06] | Резерв |

**Почему выбрано это сочетание.** Встроенный MCP-режим BSL LS выдаёт сведения о встроенных функциях и объектах платформы из того же файла BSL LS, что уже перенесён в контур. Дополнительных затрат это не требует: если режим не заработает, его отключают настройкой `disabled`, и остальная система продолжает работать. Базовые знания языка BSL у модели есть, а файл правил задаёт стиль кода.

**Почему не синтакс-помощник.** Он точнее (около 23 тыс. документов справки, карточка с сигнатурой и контекстами [R04]), но требует Docker и Elasticsearch. Для изолированного контура без Docker и без прав администратора это неприемлемо (Кр-1).

**Остальные:** ИТС закрыт подпиской и не даёт программного доступа. Свой разбор `.hbk` возможен, но это отдельная разработка без доказанной необходимости.

**Цена выбора:** MCP-режим экспериментальный и требует 2–4 ГБ памяти; без него за точность описания встроенных функций отвечает только модель.

**Пересмотреть, если:** на приёмке (вопрос 9) или в работе агент регулярно ошибается в сигнатурах платформы. Тогда — инструмент поиска по `shcntx_ru.hbk` внутри `1c-config`.

### 17.7. MCP-клиент в VS Code

**Критерии:** Кр-7 (конфиг в проекте), подключение к OpenAI-совместимому API, управление таймаутами и автоодобрением, то, что уже стоит.

| Кандидат | Вердикт |
|---|---|
| **Zoo Code / Roo Code** [R02] | **Выбран** |
| Cline [R02] | Ближайший соперник, отклонён |
| GitHub Copilot [R02] | Отклонён |
| Continue, Cody [R02] | Отклонены |
| Cursor | Вне скоупа (не VS Code) |

**Почему выбран Zoo/Roo Code.** Проектный `.roo/mcp.json` лежит в git и подхватывается каждым, кто открыл проект (Кр-7). Правила разложены по режимам (`.roo/rules/`, `.roo/rules-code/`). Есть `timeout`, `alwaysAllow`, `disabledTools` и подстановка `${env:VAR}` [R02] — всё, что нужно для схемы §14. Кроме того, он уже установлен и подключается к любому OpenAI-совместимому API, в том числе к адаптеру внутренней модели; замена клиента добавила бы риск без ощутимой пользы.

**Почему не Cline.** У Cline самая зрелая поддержка MCP и больше всего статей сообщества 1С [R02]. Однако список серверов Cline хранит в профиле пользователя VS Code (`cline_mcp_settings.json`), а не в проекте, поэтому сохранить его в git нельзя. Для команды пришлось бы раздавать инструкцию вместо готового файла. Серверы при этом совместимы: для перехода на Cline достаточно перенести один блок настроек.

**Остальные:** Copilot требует подписки, а подключить в нём внутреннюю модель нельзя или неудобно; у Continue YAML-конфиг, несовместимый с остальными; у Cody MCP только в Agent mode [R02].

**Цена выбора:** Zoo — форк Roo: документация Roo может не совпадать с поведением форка.

**Пересмотреть, если:** форк перестаёт развиваться или ломает MCP. Тогда Roo Code (конфиг тот же) или Cline (перенести блок `mcpServers`).

### 17.8. Транспорт MCP

**Критерии:** Кр-6, безопасность (нет сетевой поверхности), Кр-7.

| Кандидат | Вердикт |
|---|---|
| **stdio** [R01] | **Выбран** |
| Streamable HTTP [R01] | Ближайший соперник, Ф3 |
| SSE | Отклонён (устаревающий транспорт) [R01] |

**Почему выбран stdio.** Сервер работает как дочерний процесс агента: не нужны сетевой порт, аутентификация и служба Windows. Запуском и остановкой сервера управляет агент. Это сводит к минимуму возможности для атаки и не требует администрирования (Кр-6).

**Почему не Streamable HTTP.** Он позволяет держать один сервер на всю команду и одну выгрузку. Однако тогда нужны аутентификация, шифрование (TLS), служба Windows и открытый порт; для пилота с одним пользователем эти затраты не оправданы.

**Цена выбора:** у каждого разработчика свои процессы и своя копия выгрузки; JVM на каждой машине.

**Пересмотреть, если:** в Ф3 три и более разработчика работают с одной выгрузкой. Тогда Streamable HTTP с OAuth2 через прокси (§1.1, строка 8).

### 17.9. Правила для агента

**Критерии:** Кр-5 (лицензия), привязка к нашим инструментам, краткость (промпт тоже тратит контекст — Кр-4).

| Кандидат | Вердикт |
|---|---|
| **Свои `.roo/rules/` (3 файла)** | **Выбран** |
| `ai_rules_1c` (comol) [док] | Ближайший соперник, Ф2 после проверки права |
| Полный текст стандартов its.1c.ru | Отклонён: объём, подписка |
| Без правил | Отклонён: агент не знает порядок инструментов |

**Почему выбраны свои.** Три коротких файла описывают то, чего не знает ни один чужой набор: порядок вызова именно наших инструментов, запрет править XML, работу с ветками. Тексты свои, поэтому лицензионный вопрос не возникает. Объём небольшой и почти не расходует контекст модели.

**Почему не `ai_rules_1c`.** Это богатый и продуманный набор, но у репозитория нет лицензии. Часть файлов содержит только заголовки (полный текст отдаётся их Docker-сервером), а субагенты и команды рассчитаны на Claude Code и Cursor, не на Roo.

**Остальные:** полный текст стандартов слишком велик для промпта и закрыт подпиской; без правил агент будет читать модули целиком и править XML.

**Цена выбора:** выжимка стандартов неполная — детальную проверку берёт на себя `check_module`.

**Пересмотреть, если:** право использования `ai_rules_1c` подтверждено. Тогда полнотекстовые файлы идут в `.roo/rules-code/` (только режим Code).

### 17.10. Модель LLM

**Критерии:** конфиденциальность кода (§10); поддержка вызова инструментов; размер контекста; доступность из внутреннего контура.

| Кандидат | Вердикт |
|---|---|
| **Внутренняя модель OpenCoder через адаптер организации** | **Выбрана** (решение В-3) |
| DeepSeek API | Ближайший соперник; запасной вариант |
| Другие внешние API | Не рассматривались: тот же вопрос передачи кода наружу |

**Почему выбрана внутренняя модель.** Запросы агента обрабатываются в инфраструктуре организации, поэтому код и описание конфигурации не покидают её — главный риск §10 снимается без отдельного согласования. Контекст 270 тыс. токенов вмещает системный промпт агента, правила и ответы сервера с большим запасом. Адаптер предоставляет OpenAI-совместимый API, который Zoo/Roo Code поддерживает без доработок. Агент обращается к модели напрямую по адресу на том же компьютере, поэтому интернет для работы не нужен.

**Почему не DeepSeek.** DeepSeek уже использовался, и качество вызова инструментов у него проверено на практике — это его реальное преимущество. Однако это внешний сервис: тексты модулей уходили бы за пределы организации, и для этого потребовалось бы согласование службы ИБ. При наличии внутренней модели с достаточным контекстом такой риск не оправдан.

**Цена выбора:** качество работы агента зависит от того, насколько уверенно внутренняя модель выбирает и вызывает инструменты; адаптер — собственная разработка, его сопровождение остаётся за организацией.

**Пересмотреть, если:** адаптер не проходит проверку вызова инструментов (план, шаг 0.4), или на приёмке модель вызывает инструменты хуже 9 случаев из 10. Тогда — доработка адаптера, другая внутренняя модель или, по согласованию с ИБ, DeepSeek как запасной вариант.

## 18. ВОПРОСЫ И ОТВЕТЫ

### 18.1. Для разработчиков

**Зачем сервер, если агент и так читает файлы в `src/cf`?**
Агент умеет читать файлы, но не знает, как устроена выгрузка: что `Документ.X` — это файл
`Documents/X.xml` и до пяти модулей, что синоним «Реализация» хранится внутри XML, что модуль на
10 тыс. строк нельзя читать целиком. Сервер даёт агенту эти знания, краткие описания объектов и проверку
кода, а не дублирует чтение файлов.

**Почему не одна ветка?**
Выгрузка записывает файлы в свой каталог, не проверяя, менялись ли они. Если в том же каталоге работает
агент, его правки могут быть перезаписаны без предупреждения. С двумя ветками такая ситуация становится
видимым конфликтом слияния, который решает человек.

**Что если MCP-режим BSL LS не заработает?**
В настройках агента для него указывается `"disabled": true`. Проверка кода продолжает работать через `check_module`, а знания о языке обеспечивают модель и файл правил `20-bsl-standards.md`.

**Как быстро агент видит изменения из Конфигуратора?**
После запуска задачи «1С: выгрузить» (1–3 мин) и слияния `git merge base`. Без ручного запуска — на следующее утро, после ночной выгрузки.

**Можно ли агенту править формы и реквизиты?**
Нет. Ручная правка XML форм и метаданных — частая причина ошибок загрузки. Агент описывает изменение, человек делает его в Конфигураторе.

**Что если Планировщик запрещён политикой?**
Выгрузку запускает задача VS Code при открытии проекта (`folderOpen` с параметром `-IfOlderThanHours 12`): если последней выгрузке больше 12 часов, она выполняется заново.

**Почему выгрузка не из рабочей базы?**
С рабочей базой работают пользователи. Выгрузка её не изменяет, но создаёт нагрузку и требует пароль администратора;
ИБ разработки содержит ту же конфигурацию плюс текущие доработки.
